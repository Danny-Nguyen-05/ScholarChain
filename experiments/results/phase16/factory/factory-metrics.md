## 4. Rules (documented regexes are in `factory-metrics.json`)

- Verdict lines: a line starting with STATUS or '...verdict' and a colon whose next 220 characters contain a verdict token. A STATUS line that repeats the class of the closest preceding VERDICT-labelled line within 150 lines is a footer restatement and is not counted (listed with reason).
- Review unit: the unit id (nnX) in the verdict line, else in the nearest preceding heading, else '-' (the whole phase). First-pass acceptance = the first counted verdict of the unit is APPROVE.
- Finding lines: a numbered/bulleted/heading/table line or an id (B1, N2, F3) followed by a severity word as written. A finding restated in a recheck is counted again as a line; 'distinct' keeps one per (unit, id).
- Severity normalisation (a documented mapping, not a record): critical/blocker/high/P0/P1 -> high; major/medium-high/medium/P2 -> medium; low-medium/low/minor/P3 -> low; info/nit -> info. The 'blocking flag' is the word block/blocks/blocking (not non-blocking) in the first 300 characters of the line.
- BLOCKED-ON: lines 'STATUS: BLOCKED-ON' count as BLOCKED-ON reports; 'BLOCKED-ON OWNER:' fields that name an engineer role or the coordinator count as routed dependencies.
- Manual interventions: (a) the report-contract line 'MANUAL ACTION REQUIRED:' whose value is not none/n-a (a step an agent said only the human could take; nearly all name the human review or commit gate, so this is a gate count, not a count of unplanned interventions), counted apart from the 'none' lines; (b) the human's own quoted words or DECISION lines in human-gate.md; (c) the phrase 'manual(ly) intervention/repair/fix/edit/override' in running text.
- Guard blocks (unsafe actions prevented): a line pairing PreToolUse/guard hook/hook with blocked/refused/rejected/denied; 'fixture_or_test' marks lines that describe a probe or fixture rather than a real blocked action.

## 5. GAPs

- First-pass acceptance by owning agent: the review records name the reviewed unit and sometimes the owner of a finding, but a first-pass APPROVE names no owner, so only per-unit acceptance and owner-attributed findings are reported; a per-agent acceptance rate cannot be computed from the records.
- Ownership violations caught by the hook/guard as a count: the records mention hook blocks in prose only; the lines found are listed under guard_block_mentions, not a log-derived total (the hook writes no persistent log in the repository).

## 6. Limitations and threats to validity

- Heuristic parsing: formats differ by phase (STATUS lines, VERDICT lines, tables, verbatim external reviews); a verdict or finding written in a shape the regexes do not match is not counted, and prose that matches is counted. The audit list is the remedy: every counted item has a line number.
- Events that were not written down are not counted (for example hook blocks nobody described, repairs done inside a round without a heading).
- Phases 1-5 used external (human-supplied) reviewers and different file layouts from Phases 12-15 (code-reviewer subagent); rates are not comparable across eras.
- Severity words follow each reviewer's own scale (P1/P2, High/Medium/Low, blocker/nonblocking); the normalised table is a documented mapping.
- Repair rounds are counted from headings in repairs.md; a phase whose repairs.md has no 'repair round' heading shows 0 even if repairs happened.
- No independent ground truth for the counts exists: they were not cross-checked against a second parser.

The coordinator notes (git-ignored, local) are summarised apart in `factory-notes.md`.
