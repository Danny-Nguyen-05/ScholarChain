Interpretation limit: 7 ranking questions (3 coauthor_breadth, 1 max_team_size with a ranked key, 3 bridge) x 2 runs, of which 6 are scorable. For q03 (max_team_size) all 100 key entries tie at the same value (15) and the key keeps the first 100 by id order, so a tied researcher outside those 100 scores 0 although it ties. q03 is listed per question and excluded from the main aggregates; a second aggregate counts it at its measured 0 (a lower bound). The tie premise is tested in tie_check from the values the answer states for the three retrieved researchers outside the key (those values were checked against the export by the Q12 scorer; this script does not read the export): one states 15 (a tie cut off by the key's 100-entry limit), one states 14 (below the key's value, so genuinely not a top-ranked researcher for this measure), and for one no value is stated (the answer lists 2 of the 3 retrieved). So the 0 is only partly an artifact of the tie truncation. The same truncation can affect a few tied items at the foot of the other keys. The two runs retrieved identical lists (observed), so they are not independent samples and no confidence interval is given (n = 7 questions would make one meaningless). The key's top-100 is the corpus-wide ranking while the runtime ranks inside its bounded artifact, so P@K against the key's top-100 is a looser test than against its top-K. Graded gain = the key's metric value, a derived grade, not a human relevance judgement. K is the runtime's own context cut (3 or 4 researcher items), so recall@K against the 100-item key is not reported (it would be at most K/100 by construction).

## 6. GAPs

- **vector-only recall@K, precision@K, MRR, nDCG**: no relevance labels for any vector query and no stored ranked results; the index no longer exists
- **fused (graph + vector) retrieval metrics and the graph-only vs vector-only vs fused comparison**: no fused run was recorded; the stack was destroyed
- **graded nDCG from human relevance judgements**: no human graded labels exist; the graded nDCG above uses the answer key's metric value as the gain and is labelled as such
- **recall@K for direct-collaborator, community and path questions**: the answer's researcher list is cut by the context window (e.g. 1 of 25 coauthors listed) and the edge evidence carries no plain coauthor id field, so the retrieved set cannot be reconstructed from the stored raw; the scorer's pass/fail is the only measure
- **retrieval latency by stage**: only end-to-end latency and the S3 Vectors SDK call time (n = 5) were recorded; see the performance group

## 7. Threats to validity

- The answer key is derived by the same repository (an independent Python port of the Spark metrics); it was reviewed, but it is not an external gold standard.
- 7 ranking questions and 33 questions in total: no per-type inference is possible, only descriptive rates.
- The retrieval list order is taken to be the order of explain.body.evidenceIds (the runtime's own ranking); the order was not independently logged.
- The Q12 questions were authored with the system's capabilities in mind (3 per type, thin-data topics deliberately included as abstention tests), so the pass rates measure coverage of designed query types, not open-domain retrieval.
- The vector smoke is a known-item test on the stored text itself and overstates retrieval quality for novel queries.

## 8. Metric definitions

- precision_at_k: hits in the first K / K
- recall_at_k: hits in the first K / relevant
- reciprocal_rank: 1 / rank of the first relevant item, 0 if none
- ndcg_at_k: DCG(retrieved)/DCG(ideal), DCG = sum gain_i / log2(i + 1), ideal = the K largest labelled gains; null when the ideal is 0
