# EMR feasibility design proposal — no launch authority

Base release: 2d637c6707ecc66a489561dd179406b6ac622e93, branch phase-12. Checked 2026-11-03. Public documentation and existing approved evidence only. This report proposes the next design; it creates no runnable Terraform, resource, grant, executable bootstrap or approval. The old zero-resource preparation root remains historical and unmodified.

## Fixed scope and choice

Retain one primary plus one core m5.xlarge in us-east-2, no task/Spot nodes, no scaling, one cluster attempt and two hours maximum total cluster lifetime including startup/failure/teardown. USD 5 is a proposed suballocation of the shared USD 200, not new funds. Root coordinator supplies the current all-resource model; public rates alone cannot establish current account allowance or capacity. There is no fallback to Serverless/EKS, larger instances, an extra attempt or a different budget without a new human decision.

Recommend EMR 7.8.0 as the *compatibility experiment candidate*: its public page lists Hadoop 3.4.1, managed Spark 3.5.4-amzn-0/Scala 2.12.18, Corretto 17 and standard-support end 2027-03-06. This selects a matching major Spark context for investigation, not stock binary compatibility. Exact regional release/instance/quota availability and current security advisories still need preflight. Later 7.x/8.x releases are not silently substituted. [emr780]

The approved source release has a packaged job JAR 11,732,592 bytes / SHA256 d52f11ebad5ec9e1ffdd1910d562023e934ce7ab62e7c74a5ffd650f8951b86b. Preserve those bytes. A changed jar requires a new local baseline; no run-ID normalization is authorized.

Build owner should next produce a checksummed immutable *custom runtime bundle*, rather than execute /usr/bin/spark-submit or load /usr/lib/spark. It must use exact Apache Spark 3.5.4_2.13 classes, Java 17, the locally verified coherent Scala-library/reflect 2.13.14 and Scala 3 library 3.3.4 bytes. Upstream spark-3.5.4-bin-hadoop3-scala2.13 scripts/launcher are a candidate input only; no binary was downloaded or inspected here. Verify its official checksum/signature and actual JAR inventory before staging. An upstream filename alone is not proof that its Scala library matches the job. The prior Phase6 memo’s upstream Scala 2.13.8 versus retained Scala 2.13.14 patch observation alone is not a proved failure, but arbitrary mixed duplicates are unacceptable.

The local readiness runtime has 146 JARs with exact loaded class/source hash evidence, and its standalone probe needed an additional POM-pinned Scala XML 2.1.0 artifact. Package the selected required launch/runtime files explicitly; do not assume those local cache symlinks form a portable distribution. Avoid duplicate *versions* and bind the exact effective driver, AM and executor classpath. Any byte-identical localization duplicates must be documented, not confused with conflicting Scala versions. Stock EMR Spark/Scala 2.12 and Amazon-specific Spark connector JARs must not enter the custom runtime by ambient CLASSPATH, SPARK_DIST_CLASSPATH or wildcard /usr/lib paths.

Submit through the isolated bundle in YARN cluster mode. HADOOP_CONF_DIR/YARN_CONF_DIR use the actual EMR client configuration. Propose spark.yarn.populateHadoopClasspath=false for the prebuilt with-Hadoop variant, and stage an exact spark.yarn.archive or jars inventory. The Apache source documents these mechanisms; it does not certify Hadoop 3.3.4 client libraries against this EMR Hadoop 3.4.1 / YARN server. Configure the bundle's Java 17 and Scala binary version explicitly. Do not use userClassPathFirst as an assumed fix. [yarn354]

Before the real pipeline, require an actual executor outside the driver to read/write the selected shared path, report loaded Spark/Scala/reflect/Scala 3 classes and artifact hashes, and perform a bounded distributed DataFrame/Parquet roundtrip. A failed linkage/serialization/mount probe ends the single attempt; no on-cluster dependency repair/retry. Then run the same job/config/upstream manifests preserved and compare all 28 datasets against the approved local baseline. Remote timestamps/physical paths may differ; semantic/run/code/input fingerprints and all rows must not be rewritten to force equality.

## Shared filesystem recommendation and alternatives

Recommend a new encrypted Regional EFS Standard filesystem with Elastic throughput as the proposed working filesystem. One private same-AZ mount target serves both nodes, and an access point enforces a dedicated POSIX identity/root. Both nodes mount the same access point at /mnt/scholarchain/spike/<operation>; operation is a future gate input, not an invented executedID. Configure fs.defaultFS=file:/// for this candidate only. All config/upstream/output/checkpoint/event paths use this same absolute mount. S3 remains artifact/log transport, not a JavaNIO mount. Local executor spill stays on encrypted local EBS. Access point and TLS/IAM mounting capabilities are documented, but no actual mount/helper compatibility or throughput was tested. [efs-access point,efs-iam,efs-tls]

Terraform must create the filesystem, KMS binding, explicit filesystem policy, access point, mount target and dedicated NFS security group. Deny anonymous/insecure access; require TLS/access point, scoped ClientMount/ClientWrite, no general ClientRootAccess. Mount target TCP 2049 ingress is only from this spike's two node groups. Match the enforced POSIX identity/permissions on both nodes; prevent input/config mutation by executor tasks and keep separate writable output roots. Verify mount source and sentinel exchange; an existing ordinary directory after mount failure is not acceptable fallback. Lifecycle helper package and its RPM dependencies must be pinned/tested before any launch.

Primary-node NFS would avoid EFS billing but makes the primary a storage failure domain, adds server/export/authentication/TLS complexity and can lose data on bootstrap failure or primary termination. It is not preferred under the preserved transit-encryption requirement and has no proven implementation. HDFS/S3A would require separately scoped Spark/core/NIO adaptation, new test/review/baselines; HDFS pathnames alone do not satisfy JavaNIO. Those are future alternatives, not quiet substitutions or reasons to weaken completion checks.

EFS Elastic read/write metering includes minimum request sizes. Physical fixture/archive bytes cannot prove a metered read/write ceiling. Root's diagnostic bounds must remain model assumptions until runtime measurements/guard policy can bound them. Regional storage, throughput, request/data transfer, retained bytes and minimums all require explicit prices and allowance; no free-tier assumption.

## Isolated network, storage and encryption

Propose a dedicated VPC with one private subnet for both nodes/EFS mount target and one public subnet only for a NAT gateway/EIP, plus IGW, route tables and a restricted S3 gateway endpoint. Nodes have no public IP, no SSH/keypair ingress and no public UI. Distinct custom EMR primary/core/service-access groups and an emptied default SG are mandatory. Use the current official managed private-group rule table; EMR adds required rules, so effective rules after launch need inventory. The existing general module's same primary/core SG is not reused as evidence of this design. [security-groups]

The S3 gateway endpoint policy must include exact necessary EMR/Amazon Linux repository buckets and reviewed project artifact/log prefixes, with IAM and resource policies also scoped. Do not block EMR bootstrap by allowing only our bucket. The NAT candidate covers regional control/API/bootstrap requirements that are not supplied by that gateway; port 443 egress through NAT is not a domain-level allowlist. Package/stage runtime inputs ahead of launch to avoid arbitrary internet installers. Price all NAT/EIP hours and bytes including setup/teardown and partial-hour rounding. A NAT-free multi-interface-endpoint topology is an alternative only after enumerating every required service/repository and comparing total cost; zero NAT does not imply zero egress cost. EMR 8 control-plane endpoint requirements are not asserted for 7.8. [private-subnet,private-s3]

Create private same-region S3 artifact/log/evidence prefixes with ownership enforcement, block public access, TLS-only policy and SSE-KMS. Encrypt EBS root/data with the selected regional symmetric CMK and default gp3 performance unless actual EMR configuration requires more. No TLS private key/certificate archive containing private keys is committed. A separately reviewed protected generation/staging procedure must establish EMR security configuration transit material. The node profile's KMS decrypt/use and EMR service role's EBS grant permissions differ; grant exact principals/context with lifecycle dependencies and no Lake Formation-enabled workload. [emr-encryption]

The custom Spark distribution must not assume it inherits EMR's managed Spark security configuration. Explicitly propose spark.authenticate=true, spark.network.crypto.enabled=true, spark.network.crypto.authEngineVersion=2, spark.network.crypto.cipher=AES/GCM/NoPadding, spark.network.crypto.saslFallback=false and spark.io.encryption.enabled=true, subject to exact-version validation. Disable external shuffle service and dynamic allocation for the one-core fixture; this avoids silently loading EMR's Scala 2.12 shuffle plugin. Disable application UIs or supply reviewed TLS/authentication settings for every exposed UI; private subnets alone do not encrypt RPC. Apache Spark 3.5.4 documents per-application YARN secret distribution and says its security depends on YARN RPC encryption, so verify the effective Hadoop RPC privacy settings on both driver/executor. Protected certificates/secrets, actual negotiated RPC encryption and failure on insecure downgrade are later implementation/canary acceptance requirements. No secret values are written in this proposal. [spark-security,emr-data-encryption]

Use one proposed spike CMK shared only by its specifically reviewed services rather than assuming the course key exists. If key/log/evidence retention is 31 days in the model, count that period; do not cost all retained resources as two hours. CloudWatch logs/guard journal/alarms/DLQ, S3 versions, requests, KMS operations, artifact upload/egress and tax/uncertainty remain in the same USD 5 proposal.

## Identity separation

A future short-lived non-root deployment role is separate from the existing billing deployer, EMR service role, EC2 node profile and watchdog execution role. The billing role is not widened or used as launcher. Terraform authoring must provide scoped resource/tag/region conditions, exact PassRole principals/services, KMS grant separation and a reviewed permissions boundary where applicable. No IAM policy or role is installed by this report. Tagging privilege must not let the launcher remove/retarget the lease or broaden stop permissions; actual IAM effectiveness is a later review/preflight item. [tag-access]

## Proposed elapsed-lifetime controller and unresolved scope race

Recommend a Terraform-authored cloud guard outside the EMR VPC: one recurring EventBridge Scheduler invokes a dedicated Lambda, with protected same-region S3 lease/state, deterministic logs, retries/DLQ and an alarm. The guard is independent of the human Terminal and cluster bootstrap. This is a design, not an implementation or hard billing cap. Scheduler precision 60 seconds and throttle/retry delays mean reserve headroom is necessary. TerminateJobFlows is asynchronous (documented 1–5 minutes, not an upper-bound guarantee). Idle auto-termination remains a short secondary safety aid, not the elapsed guard. [scheduler,scheduler-quotas,lambda-retry,terminate,idle]

Sequence: provision and verify guard before RunJobFlow; arm a new fixed UTC operation lease before creating the cluster or allowing submissions; measure from that arm/start boundary so all startup counts. Guard preflight must prove actual successful invocations, least privilege, lease/hash/deadline binding, denied unrelated cluster/region operations, no disable/extend rights for node profile and enough remaining time. Require a healthy current heartbeat and readback immediately before create. If guard unhealthy or deadline unknown, there is no launch. Example proposal: stop submissions by T+80 minutes and request termination by T+90 minutes, leaving 30 minutes within the 2-hour cluster maximum. These are proposed relative cutoffs, not a chosen human execution window.

The cluster ID is unknown before create: a schedule armed only after a successful Terraform apply leaves a real orphan race. Do not call that arrangement adequate. Preferred candidate uses a create-required immutable operation tag, fixed account/region and creation-time window; a prearmed guard may discover only that operation's cluster and bind its returned ID once into protected CAS/versioned lease state. Conditional TerminateJobFlows must be limited to that unique operation tag until exact ID is bound, then exact cluster ARN. Read-only ListClusters/Describe discovery may be broader than mutation permissions and must be disclosed. AWS documents tag-based termination and warns that tagging can bypass intent. Exact policy behavior, eventual tag visibility, discovery pagination, duplicate bindings and permission-boundary effectiveness need offline policy tests and a later actual canary. There is no proved way here to claim the unknown-ID gap closed; it is a blocking implementation acceptance condition. [tag-access]

At deadline or bootstrap/submission/mount failure, guard sends idempotent termination for its bound cluster, confirms terminal state/instance inventory and escalates if confirmation fails. No automatic new cluster/extra attempt. Guard cannot assume S3 retained log success on termination; preserve approved available evidence first without delaying termination. A deleted/wrong lease or failed invocation must raise alarm; if the cluster already exists, the human incident path must retain exact IDs and act under reviewed recovery authority. A single cloud-service guard cannot guarantee stop during regional outage; bounded residual risk and cost headroom remain human acceptance items.

Cluster termination does not delete NAT, EIP, EFS, KMS or retained storage. Therefore require a second independent, Terraform-authored cleanup workflow before launch, not a promise that a human will eventually run destroy. Proposed implementation: the prearmed guard starts a dedicated Step Functions Standard workflow (or equivalently reviewed bounded stateful Lambda sequence) outside the EMR VPC. It checks cluster terminal state and exact EC2/EBS inventory, captures the approved available outputs/logs to the private evidence prefix with checksums, deletes the exact operation NAT gateway and waits until deleted before releasing its EIP, then deletes the dedicated ephemeral EFS mount target/access point/filesystem after approved archive completion. It records every observed transition and residual ID. Its mutations are exact-resource requests, constrained by account, region, operation identity and separately reviewed IAM support; no broad delete-by-name. Dynamic IDs must be discovered or bound into protected S3 state during provisioning, with the same prearm/unknown-ID race analysis as the cluster. Retain S3 evidence and its CMK under the proposed 31-day allowance; do not delete a key while retained objects need it. Reconcile intended emergency-controller drift with the later Terraform destroy/state workflow; all automation itself is authored by Terraform and included in the human rollback/cleanup gate.

The cleanup workflow is a mandatory design dependency with offline failure tests for delayed termination, NAT pending/deleting states, EIP-in-use, EFS client/mount dependencies, wrong/untagged ID, duplicate/tagged resources, lost lease, archive failure, denied deletion, service errors and incomplete inventory. Original G1 inputs/local baseline/human evidence are outside its deletion scope. If protected grading evidence cannot be archived, do not silently delete it to claim a cost bound: the failure is an incident and residual allowance/retention must be decided before launch. Demonstrating this failure policy, exact IAM scoping and eventual resource confirmation is required before the design can advance. Include bounded workflow transitions, S3 control operations and logs in the model. Terraform destroy remains the final reconciliation, but exit0 alone is insufficient.

A proposed ancillary target is removal by T+180 minutes, allowing setup and cleanup time beyond the cluster's 120-minute maximum. This is a conditional planning lifetime, not a proven upper bound: the controller, API permissions, archive mechanism and failure handling are not implemented or tested. If the residual cannot be bounded and accepted within USD 5, stop before launch. Do not widen the allowance or claim a hard billing cap.

## Gate and ownership dependencies

1. Human/coordinator: source-dated prices, complete all-resource cost model, conservative account-wide remaining allowance including delayed unreported usage and existing commitments; no paid Cost Explorer API or assumed credits. Proposed shape/region/cap/one attempt/lifetime unchanged.
2. Build owner: verify/pin custom runtime inputs and portable archive; exact artifact inventory/class origins and coherent Java/Scala; no ambient EMR classpath.
3. Infra owner, new bounded work order: author isolated network/EFS/IAM/encryption/cloud guard roots with mock/static failure tests, no live provider reads/apply. Preserve old zero-launch proposal/main course environment. Prove guard ID race handling and residual cleanup behavior before calling runnable-plan ready.
4. Spark owner only if new behavior needed: distributed Parquet probe or filesystem adaptation; corresponding feature gates and renewed baseline. Existing approved same JAR/readiness tools otherwise reused unchanged.
5. Independent review: code, policy, models, offline tests, retention/delete dependencies and all unresolved conditions. New committed release/clean checkout before live.
6. Human: approve separately bounded identity/account read preflight, genuine isolated plan/checksum, exact dated cap/runtime/region/types/counts/teardown window. No personal approval is written by an agent. Guard arming resources cost money too; their apply must be inside the later explicit gate.
7. Deploy owner: foreground single attempt, actual remote probe/class origins/all 28-table comparison, stop on first failure, termination plus destroy and after-inventory. No phase completion until truthful acceptance evidence.

## Cost fit and throughput alternative

Coordinator’s fresh conditional model is approximately USD5.30 for the nominal Elastic case, after its stated reserve/tax assumptions. A stress case with higher EFS metering/log volume is approximately USD6.21. These are coordinator calculations, not independently computed here or an account observation. The primary nominal model exceeds USD5 and cannot certify a safe fit from physical fixture bytes or the old compute-only subtotal. Keep launchable=false until quantities and failure cleanup are credibly bounded.

For comparison only, Regional General Purpose Bursting can remove the Elastic per-GB throughput line while retaining TLS/IAM/access points. AWS documents a 1MiBps metered floor even when the baseline is lower, with credit-dependent burst behavior. This is not a throughput observation or a promise that the complete job finishes within the selected cutoff. A later proposal could choose this mode to reduce variable-cost uncertainty; do not silently change the current Elastic draft or buy storage to manufacture credits. Current performance documentation also lists One Zone Elastic: do not claim it is universally unsupported. Regional remains the proposed filesystem type. [efs-performance]
