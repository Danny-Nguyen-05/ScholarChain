# Deployment-identity establishment — proposal for human review

This is an offline preparation document. It grants no permission and does not authorize a console exception, IAM creation, apply or paid work.

The only confirmed identities are the MFA-protected root and scholarchain-planner. The planner remains read-only, including no added AssumeRole grant. No privileged non-root bootstrap identity or actual trusted operator ARN has been supplied. The policy draft is therefore not an executable identity-establishment plan.

Preferred route: if a separate, already-authorized privileged non-root identity exists, the human identifies it and its temporary-credential authentication method. A later bounded work order authors Terraform for the exact billing deployment role, trust and caller attachment, with five required tags. Its plan, checksum, independent review and explicit human-written security-change approval are separate gates. Root does not run Terraform.

If no such identity exists, the human must first decide whether to authorize a narrowly documented one-time account-bootstrap exception to the Terraform-only rule. The proposed exception is limited to human-performed root-console account access setup: establishing a distinct console operator and its MFA, plus the single billing role with the exact reviewed trust, caller and execution documents. It excludes broad AdministratorAccess, planner changes, root CLI/access keys, budget creation, course infrastructure and EMR. The actual operator ARN, temporary-session workflow and exact resources must be reviewed before the human records any exception. Subsequent Terraform ownership or adoption of those manually created IAM resources requires a separately reviewed procedure; do not import ad hoc or create duplicate owners. No exception is approved here. Do not enable AWS Organizations as an incidental setup step.

The new policy-only root documents one conservative IAM-user trust option with MFA-conditioned STS assumption. It does not prove that aws login forwards the MFA context required by that trust. If the chosen authentication path cannot supply that context, stop and review the identity/trust design rather than weakening the condition or creating permanent access keys. Federation is an alternative design requiring its own explicit trust/MFA review.

After establishment, verify the dedicated non-root temporary identity under a separately authorized read-only check. Recreate the private budget recipient input outside Git and produce a fresh billing plan with that identity. The old planner-bound plan and private directory were deleted by the human; historical checksum evidence is not an execution artifact. Independently review the fresh plan and obtain human-written apply approval before creating the budget. Then verify all five tags, custom period, before-credit accounting basis, notifications and recipient delivery. Usable cost data and conservative remaining allowance are still required before any paid EMR work.

No approval is inferred from the user requesting this draft. Every EMR bundle, same-JAR baseline, runtime/class-origin probe, shared filesystem, independent elapsed-time deadline, isolated plan, execution cap and teardown gate remains open. The USD 5 proposed spike allocation and USD 10 remaining all-EMR reserve are not spending approvals.
