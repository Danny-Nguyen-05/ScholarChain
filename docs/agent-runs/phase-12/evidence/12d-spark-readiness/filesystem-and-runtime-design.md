# Offline runtime and filesystem contract

The current application uses Java NIO for config, upstream manifests/completion checks, local event logs and metadata; Spark reads/writes bare paths derived from those same roots. This is verified from Phase6Main, Phase6CReaders and Phase6Export source, not a claimed cloud observation. A working bootstrap installation alone cannot make driver-local files visible to executors on other machines.

## What this round can establish locally

- An upstream-complete synthetic G1 bundle generated by unchanged Hadoop and disabled-LLM ER entry points can be copied without changing bytes. Spark reader inventory/completion checks bind relative export files and manifest hashes. A relocated input-root run tests portability at the consumer boundary; it does not rerun upstream transformations or claim new observations.
- The current assembled job JAR, its SHA256 and actual loaded class bytes/origins must be bound for both baselines. Loose class-directory runs are not interchangeable with a job JAR because Phase6Main.codeFingerprint binds its actual code source.
- Identical JAR, unchanged upstream manifests and identical logical settings should give exactly the same runId/context.runId across physical root or shuffle changes. The comparator must preserve full provenance and recompute actual rows/counts/hashes. A failure is evidence to investigate, never permission to erase differing lineage.
- Spark local[2] runs tasks in its driver JVM. A distinct local-cluster executor can prove a separate task JVM and same-machine shared-path exchange only. It is neither an EMR/YARN compatibility proof nor a multi-host mount proof.

## Requirement for a future remote run

Every NIO and Spark input/output/checkpoint path must resolve to the same absolute POSIX shared location on the driver and each executor. With an explicitly selected shared POSIX mount, Hadoop fs.defaultFS=file:/// makes Spark bare paths use that mount, but the setting alone never turns independent node disks into shared storage. Before remote Phase6Main, the reviewed probe must demonstrate driver-to-executor read and executor-to-driver write visibility on that exact path and collect actual non-driver executor identities/class origins. Future deployment must account for mount permissions, encryption, availability, provisioning and teardown costs. No shared filesystem resource or application path adaptation is authored in this round.

A later infra design could supply a true shared mount, or the module owner could receive a separate application-adaptation work order for a distributed filesystem. Neither option is selected or costed here. Remote filesystem proof, Scala/YARN compatibility, deadline termination, real isolated plan, human runtime/spending/teardown approval and after-inventory remain open.

## Primary references and limits

- Spark v3.5.4 submitting-applications source: https://github.com/apache/spark/blob/v3.5.4/docs/submitting-applications.md — assembly packaging keeps runtime Spark/Hadoop provided; local[K] is a threaded local master, and application artifacts must be available to the cluster.
- Spark v3.5.4 LocalSparkCluster source: https://github.com/apache/spark/blob/v3.5.4/core/src/main/scala/org/apache/spark/deploy/LocalSparkCluster.scala — test master/workers share the driver process, while launched executors use separate JVMs. Therefore only actual task identities, not master labels alone, establish a non-driver process.
- Hadoop3.3.4 default configuration: https://github.com/apache/hadoop/blob/rel/release-3.3.4/hadoop-common-project/hadoop-common/src/main/resources/core-default.xml — fs.defaultFS defaults to file:/// and controls unqualified filesystem resolution. This does not establish node-to-node storage sharing.
