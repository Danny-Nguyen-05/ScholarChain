# Phase 6 Spark analytics design

This document began as the 6B design for eleven distributed Spark jobs. Jobs 1–2 are implemented in `Phase6CJobs`, jobs 3–8 in `Phase6DEJobs`, jobs 9–10 in `Phase6FGJobs`, and Job 11 in `Phase6Export`. `Phase6Main` runs the complete pipeline. The [course Spark requirements](https://github.com/0x1DOCD00D/ScholarChain/blob/main/README.md#detailed-spark-requirements) require an input/output and physical-execution account for every job. The core wire examples and version constants define the serialized fields.

## Shared input, output, and execution rules

One run reads one **completed** Hadoop J01–J09 export and one **completed** entity-resolution export. Their manifests, completion markers, policy hashes, run IDs, and source snapshots must agree with the Spark config before data is written. Hadoop input kinds are `work`, `author-mention`, `authorship`, `team`, `pair`, `venue`, `institution`, `topic`, `enrichment`, `mention-affiliation`, `index`, `graph-edge`, `match-candidate`, and `reject`. Entity-resolution input includes researcher and work accepted links, the complete grouping constraints, unresolved/conflict decisions, its manifest and marker. Spark depends on core and reads the Hadoop and ER files; it does not depend on either producer module. All JSON-lines readers use explicit `StructType` definitions checked against core wire examples, including nested values, optional fields, enum strings, and vectors. Malformed rows enter a counted reject output via the corrupt-record column. Unsupported versions fail the run.

All graph-sized inputs, intermediate tables, joins, and aggregations remain distributed `DataFrame` operations. No RDD, GraphX, GraphFrames, Scala Spark implicits, typed case-class `Dataset`, or whole-graph driver collection. A single allowlisted bounded-action helper will own driver actions: counts, single-row aggregates, and explicitly capped result sets. Existing domain records retain their `scholarchain.domain.v1` wire shape and `Provenance`; every new analytics record uses `SparkRecordContext(schemaVersion = scholarchain.spark-analytics.v1, runId, windowId, lineage)`. `SparkLineage` binds Hadoop run/snapshot and ER run/policy version/hash, with source work and mention IDs where applicable. The run ID is a deterministic hash of the two input manifest bindings, config fingerprint, identity and representative policy versions, and code version. Rows sort by stable primary key within each Parquet partition; part-file names are not part of logical equality.

The selected `SparkWindow` IDs are `all-years` (both year bounds absent), `through-2009` (open lower bound), `2010-2014`, `2015-2019`, `2020-2026`, and cumulative `since-2015`. The four non-overlapping periods have comparison orders 0–3 and are the only delta-comparison sequence. Identity grouping happens once over all years. Year-bounded windows exclude works with missing DBLP year and count them; all-years includes them. `SparkAnalyticsConfig` at `scholarchain.spark-analytics-config.v1` holds input/output roots, these windows, identity/representative/graph policy versions, component/community/k-core iteration limits, checkpoint directory/interval, hop limit, `BenchmarkPair` selections, sample sizes and seed, representative-work cap 5, maximum-team work-ID cap 20, shuffle partitions, and hard-invariant behavior. The checked-in example is `modules/core/src/main/resources/scholarchain.spark-analytics-config.v1.json`; it is a local placeholder, not an observed source run. Local test sessions use `local[2]`, four shuffle partitions, disabled UI, UTC session timezone, explicit warehouse directory, and a temporary checkpoint directory.

| Logical output | Core wire record and version |
|---|---|
| Canonical nodes and non-coauthor graph edges | Existing `GraphNode`, `GraphEdge` at `scholarchain.domain.v1`; frozen `CoauthorEdge` and `ResearcherMetrics` remain readable for prior consumers |
| Weighted coauthor edges and support | `SparkCoauthorEdge`, `CoauthorEdgeSupport`, `scholarchain.spark-analytics.v1`; frozen numeric-window `CoauthorEdge` remains readable |
| Collaboration metrics | `ResearcherMetricsDetail`, the additive companion to frozen `ResearcherMetrics`, `scholarchain.spark-analytics.v1` |
| Components | `ComponentMembership`, `ComponentSummary`, `scholarchain.spark-analytics.v1` |
| Communities | `CommunityMembership`, `CommunitySummary`, `CrossCommunityEdge`, `scholarchain.spark-analytics.v1` |
| Paths | `PathEvidence`, nested `PathHop` and `PathStatus`; `PathLengthEstimate`, `scholarchain.spark-analytics.v1` |
| Bridges and coreness | `ResearcherBridgeMetrics`; coreness also appears in `ResearcherMetricsDetail`, `scholarchain.spark-analytics.v1` |
| Deltas and summaries | `TemporalChange`, `SemanticSummary` with `SummarySourceRef`, `scholarchain.spark-analytics.v1` |
| Audit and handoff | `IntegrityViolation`, `SparkCounter`, `LoadManifest`, `scholarchain.spark-analytics.v1` |

The new types above are declared in `SparkAnalyticsContracts.scala`; the sixteen `modules/core/src/test/resources/wire/spark-*.json` examples show their exact serialized fields, nulls and enum values. `ResearcherMetricsDetail` includes component ID and optional community/coreness, so Job 3 first computes its numeric intermediate and publishes the final companion row after Jobs 4, 6 and 8 have supplied those fields. No fake component ID is inserted to make an early row fit the final schema. The frozen `CoauthorEdge` has integer window bounds and collaboration years, so it cannot honestly express an unbounded all-years edge supported only by yearless works. `SparkCoauthorEdge` carries the explicit `windowId` in its context and optional first/last years; it is the Phase 6 edge contract without changing the frozen wire. An all-years edge supported only by yearless works has both collaboration-year fields absent, while each `CoauthorEdgeSupport` row retains its optional source year.

The normal output root is `target/phase6-runs/<runId>/`; the same relative layout can be placed under `s3://scholarchain-graph/`. Job outputs below name logical tables; their exact core record names and serialized fields are bound to the 6B core examples. No job assumes a graph-sized broadcast. Broadcasts are allowed only for manifest/config scalars or a measured, explicitly bounded lookup; Spark must use shuffled joins otherwise. Persist a reused canonical identity mapping, authoritative teams, windowed edges and memberships only when consumers justify it, materialize before reuse, and unpersist afterward. Persisted tables do not replace checkpointing of iterative lineage. Capture `df.explain("formatted")` for each meaningful output, enable an event log, and summarize stage task/partition counts, shuffle bytes/records, durations and failed tasks. Driver memory must hold only job metadata, counters, explicit bounded samples, and selected path results, never vertices, edges, teams, or all work IDs.

## Job 1 — Canonical researchers, works, authorship and context

**Inputs and versions.** Completed Hadoop `work`, `author-mention`, `authorship`, `team`, `venue`, `institution`, `topic`, `enrichment`, `mention-affiliation`, and `graph-edge` records at `scholarchain.domain.v1`; ER researcher/work accepted links and complete grouping constraints at their existing core domain version; input manifests and marker formats as exported. **Outputs.** Canonical Researcher, AuthorMention, Work, Venue, Institution and Topic nodes; `AUTHORED`, `RESOLVES_TO`, `PUBLISHED_IN`, `AFFILIATED_WITH`, and `HAS_TOPIC` edges in the frozen domain format; canonical-work/member intermediates; `IntegrityViolation` rows at `scholarchain.spark-analytics.v1`. Graph nodes and edges use the existing core `GraphNodeClass` and `GraphEdgeType` wire values where applicable.

An exact DBLP author name determines the researcher ID: `researcher:dblp:` followed by SHA-256 of the identity policy version, LF, and the NFC-normalized exact name. Trimming is applied before hashing; case and DBLP numeric homonym suffix remain. Observed ORCIDs are external identifiers, not ID replacements; conflicting ORCIDs in one DBLP-name group produce a non-hard `conflicting-dblp-orcid` integrity row and `conflictingDblpOrcidGroups` counter. Accepted non-DBLP researcher links attach only when the complete constraints allow exactly one DBLP-name target. Links joining different DBLP names stay unapplied; ambiguous or unresolved mentions remain mention nodes. Accepted work links form candidate groups, but a group violating cannot-links or authoritative identifier conflicts is not merged. Representative selection prefers the `work:doi:` ID authority, then `work:arxiv:`, then a DBLP source observation, then the smallest work ID. A missing redundant `doi` column cannot demote a DOI-authority ID. The configured representative policy version is bound into logical run identity; the supported rule is this deterministic ordered authority policy. A canonical work uses only the rank-one DBLP observation's team and pair rows; the rank is `(sourceRecordId, workId)` and other DBLP observations in that group contribute to `nonAuthoritativeDblpObservationsDropped`. Enrichment-only works remain eligible for context nodes but not coauthorship metrics. Teams from multiple sources are never unioned.

**Physical plan.** Hash-partition observations and links on source endpoint / work ID for distributed joins and grouping; use the canonical work ID and researcher ID for downstream partitioning. Constraint validation may require grouped endpoint joins and shuffles; a bounded manifest or policy may broadcast, but not the complete constraints by default. Repartition at canonical keys after grouping, then cache only reusable mapping and authoritative-team tables. A checkpoint is needed if constraint/group propagation becomes iterative; it must be an explicit distributed checkpoint. Expected shuffles: deduplication, accepted-link grouping, constraint checks, representative selection, mention-to-researcher joins and team deduplication. No planned coalesce before these joins; output writers may coalesce only after measured partition sizes show it is safe. The driver holds only manifests and counters.

**Integrity and counters.** No forbidden merge, no two different DBLP names forced together, and every `AUTHORED`/`RESOLVES_TO` endpoint exists. Count malformed/mismatched inputs, unresolved and ambiguous mentions, conflicting ORCIDs, unapplied cross-name links, constraint-blocked work links, missing endpoints, duplicate team members, and `enrichmentOnlyWorksExcluded`. Integrity rows retain the offending entity key and upstream run/policy lineage; source work/mention lists and `evidenceRefs` may be empty when the pointer is to the complete upstream run. Endpoint and hard-invariant failures stop the run when the default hard-invariant flag is set.

## Job 2 — Temporal weighted coauthorship graph

**Inputs and versions.** Hadoop `pair` rows at `scholarchain.domain.v1`; Job 1's canonical work, team and mention maps at the Spark version. **Outputs.** `SparkCoauthorEdge` per window and `CoauthorEdgeSupport` for each distinct `(edgeId, canonicalWorkId, optional DBLP year)`, both at `scholarchain.spark-analytics.v1`. Paths: `edges/type=coauthored_with/run_id=.../` and `edges/type=coauthored_with_support/run_id=.../`; their contexts carry the exact `windowId`. The existing numeric-window `CoauthorEdge` and its ID formula are preserved for existing consumers, not used to encode all-years by inventing integer bounds.

Keep pairs only from the selected authoritative DBLP team observation. Map endpoints to canonical researchers; count/drop unmapped endpoints and self-pairs. Canonicalize pair order, deduplicate by canonical work and pair, then expand to windows. Weight is the count of distinct supporting canonical works. First/last collaboration years are the minimum/maximum **known** DBLP years; both remain absent when all supporting works are yearless. Keep at most five representative IDs ordered by known year descending, unknown years last, then work ID; the support table retains **every** work. `StableIds.sparkCoauthorEdgeId(a, b, window, policyVersion)` binds the Phase 6 edge ID to the configured label and optional numeric bounds, including for all-years.

### Jobs 1–2 fixture and local run interface

`Phase6CJobs.build(spark, config, input, lineage, runId)` accepts a `Phase6CInput` of normalized DataFrames. `works` has `workId, source, sourceRecordId, year, title, doi, arxivId, venueId, snapshot`, and optional `abstractTextRef`; `mentions` has `mentionId, source, sourceRecordId, nameText, observedOrcid, snapshot`; `teams` has `workId, source, sourceRecordId, memberMentionIds`; `pairs` has `workId, source, sourceRecordId, leftMentionId, rightMentionId, year`. Researcher/work accepted links and cannot links each have `leftId, rightId`; authority tables have `endpointId, namespace, value`. Link IDs are mention IDs or work IDs, with ORCID profile endpoints represented as `orcid:<value>`. Optional venue, institution, topic and enrichment tables retain their domain field names. Optional ER researcher/work unresolved/conflict tables have `decisionId, pairId, entityType, outcome, reasonCodes, policyHash`; the reader verifies their explicit decision schemas and publishes `erResearcherUnresolved`, `erResearcherConflicts`, `erWorkUnresolved`, and `erWorkConflicts` counters. Missing graph endpoints produce hard `missing-graph-endpoint` integrity rows and a `missingGraphEndpoints` counter; the hard-invariant flag controls whether the run throws after recording those rows in the in-memory result.

The result exposes `canonicalWorks(workId, sourceRecordId, canonicalWorkId, authoritativeSourceRecordId, year, hasDblp, authoritativeWorkId, groupId)`, `memberships(canonicalWorkId, workId, mentionId, researcherId, year)`, windowed `edges` and complete `support`, along with researchers, mentions, works, graph nodes/edges, integrity and named counters. `edges` includes `context, edgeId, windowId, researcherA, researcherB, policyVersion, jointPublicationCount, firstCollaborationYear, lastCollaborationYear, representativeWorkIds, windowStartYear, windowEndYear`. `support` includes `context, edgeId, windowId, workId, year`. `counters` includes `context, name, value, detail`.

The executable entry point is `Phase6CMain SPARK_CONFIG_JSON`, run locally with `sparkAnalytics/Test/runMain` on Java 17 (Spark is test/provided scoped in sbt) or with the packaged job JAR under `spark-submit`. It verifies the Hadoop and ER completion marker, manifests and file hashes (including the ER export's binding to the selected Hadoop completion), reads explicit JSON schemas, computes a deterministic logical run ID, and publishes an atomic completed output under `outputRoot/<runId>/`. Every published table has top-level `runId` and `schemaVersion` fields; normalized intermediates receive the Spark analytics schema while existing domain fields retain their version. Malformed input lines are retained under `input_rejects` with their source path, raw line, run ID and lineage, and counted as `malformedJsonLines`; schema-version and required-field mismatches fail. The driver caps its retained SQL execution and UI history (`spark.sql.ui.retainedExecutions=4`, bounded job, stage and task retention) because job 1 issues hundreds of counter queries with deep plans; without the caps the 2 GB test JVM ran out of heap. A matching completed logical run can be reused; differing or partial outputs are refused. The 6C output contains Parquet for jobs 1–2, formatted physical plans under `plans/`, a bounded Spark task-event summary in `event-log-summary.json`, and a manifest with input hashes and table counts. Later jobs and load manifests remain in their assigned subphases.

**Physical plan.** Join pair endpoints to the cached mapping by mention ID with distributed hash joins; repartition by `(window, researcherA, researcherB)` for distinct-work aggregation. The deduplication, window expansion, pair aggregation, and support write are shuffle boundaries. Broadcast only a genuinely bounded window-definition table. Cache windowed edges for jobs 3–9; no iterative checkpoint here. The driver holds no edge list. Validate the distinct canonical pair count per work equals `n(n−1)/2` for its distinct canonical team size, and count violations, unmapped pairs, self-pairs and missing-year exclusions **per bounded window**. Unknown-year works remain in the all-years graph and metrics.

## Job 3 — Researcher breadth and team statistics

**Inputs and versions.** Job 1 authoritative memberships and Job 2 weighted edges/support, Spark version. **Outputs.** `ResearcherMetricsDetail` with the existing P/C/T/A/M/W semantics plus maximum-team work IDs and tie count; `metrics/type=researcher_collaboration/window=.../run_id=.../`. The frozen `ResearcherMetrics` parser and wire format remain compatible; its integer window bounds must not be fabricated for all-years. Solo researchers must remain in output. The finalized detail record is published after component/community/coreness jobs (see shared schema table).

Per `(researcher, window)`, compute distinct publications P, distinct coauthors C, total coauthor occurrences T as sum of `(distinct team size−1)`, average A as `T/P` (zero for no publications), maximum M as max `(team size−1)`, and weighted degree W as incident edge weights. All work IDs attaining M are counted; write at most 20 sorted IDs plus the full tie count. Do not collapse these into a score. Repartition memberships by `(window, researcherId)` and edges by `(window, endpointId)`; the membership deduplication, per-researcher aggregate, endpoint expansion, and edge-weight join shuffle. Reuse cached teams/edges; no iteration checkpoint. Driver handles only aggregate counters. `W == T` is a hard invariant; record offending researcher/window/evidence keys. Count solo publications and capped tie lists.

## Job 4 — Connected components

**Inputs and versions.** Job 2 simple undirected edges and Job 3's numeric active-researcher intermediate, Spark version. **Outputs.** `ComponentMembership` and `ComponentSummary` under `metrics/type=components/window=.../run_id=.../`, including sizes, largest-component fraction and singleton count.

Iteratively replace each node label with the minimum of itself and neighbor labels using a distributed join and groupBy. Stop at zero changes; checkpoint every configured interval (default 5); fail if `maxIterations` is exhausted. Include active researchers with no edges as singleton components. The component ID hashes window, policy and minimum researcher ID. Hash-partition by `(window, nodeId)` for propagation and by `(window, componentId)` for size aggregation. Each neighbor propagation and changed-label check is a shuffle; bounded change counts are driver-safe. Cache current labels, release superseded labels and checkpoint to bound lineage. Count iterations, changed labels, components and singletons. Membership is one row per distinct active researcher; summaries group those rows into sizes and the largest/singleton statistics.

## Job 5 — Selected paths and distance estimate

**Inputs and versions.** Job 2 edges/support, Job 4 membership, selected config pairs and seeded sample sources, Spark version. **Outputs.** Path-evidence rows at `path-evidence/window=.../run_id=.../` and path-length estimate rows at `metrics/type=path_length_estimate/window=.../run_id=.../`.

Select requested IDs or exact DBLP names and a bounded number of seeded pairs in the largest component. Cross-component pairs get `no-path` without BFS. For connected pairs, run distributed frontier BFS up to `maxHops` (default 6). Each node retains the smallest immediate predecessor ID among shortest routes; the full path breaks any remaining tie. Each hop records edge ID, weight and representative works; complete support stays in Job 2. The distance estimate samples up to S sources in the largest component of each window, ordered by `xxhash64(researcherId, seed)` and stable ID. Complete multi-source frontier BFS computes ordered non-self source-to-reached-node distances. The output reports their mean and approximate empirical 90th percentile (`percentile_approx`, accuracy 10,000), actual source count, reached-pair count and seed. Singleton estimates have zero distances and reached pairs. This estimates the largest component rather than all graph components; it is not an exact graph diameter. S limits the source multiplier; targets remain distributed. The search runs to frontier exhaustion rather than truncating at the selected-path hop limit.

Adjacency is partitioned by `(windowId, src)`; frontier/visited anti-joins use `(windowId, sourceResearcherId, targetResearcherId, node)`. Frontier-to-adjacency joins, minimum-predecessor selection, visited anti-joins and distance aggregation shuffle each hop. Cache adjacency and current frontiers; checkpoint selected-pair frontier/visited lineage at the configured interval; bounded found-path result metadata is materialized after each hop to keep the stop gate from embedding the search recursively. Once a target is discovered the complete pair is removed from the frontier. Distance-estimate frontiers checkpoint after each expansion to avoid rebuilding growing reachability joins; the visited union checkpoints at the configured interval. The driver may hold only capped selected pairs and their bounded paths, not the graph or all distances. Persist counters for found/no-path/exceeded pairs, selected pairs, additional seeded pairs after benchmark deduplication, missing benchmark endpoints, and found-path hops. Actual sampled-source and reached-pair counts are fields of each `PathLengthEstimate`; no separate discovered-node counter is emitted. Found-hop evidence is checked against the support table and core validation checks hop count against ordered nodes.

## Job 6 — Communities

**Inputs and versions.** Job 2 weighted edges and Job 3's active-researcher intermediate, Spark version. **Outputs.** `CommunityMembership`, `CommunitySummary` and `CrossCommunityEdge` under `metrics/type=communities/window=.../run_id=.../` and `metrics/type=cross_community_edges/window=.../run_id=.../`.

Start every node with its own ID. In synchronous weighted label propagation, adopt the label whose incident edges have greatest summed weight, breaking ties by the smallest label. Stop at no changed labels or default 20 iterations. Non-convergence is reported with final changed count and the number of iterations performed for each window. Synchronous propagation always swaps labels forever on an isolated two-person component, including G1 H–I; real-data windows containing such components therefore report `converged=false` at the configured limit. Its partition depends on update/tie rules. Hash community ID from window, policy and final label. Repartition by `(window, nodeId)` for propagation and `(window, communityId)` for summaries. Neighbor-label joins and vote groupBy are shuffles each iteration, followed by edge-to-membership joins for cross-community totals. Cache current labels and edges; checkpoint every configured interval. Driver stores only iteration counts. Membership uses one row per active node; summaries group membership by community, count changed labels, first convergence iteration per window and cross-community edges.

## Job 7 — Bridge measures

**Inputs and versions.** Job 2 simple edges/weights and Job 6 community membership, Spark version. **Outputs.** `ResearcherBridgeMetrics` under `metrics/type=bridges/window=.../run_id=.../`.

For each researcher, report `crossCommunityDegree` (distinct direct coauthors in other communities), `crossCommunityWeight` (sum of their edge weights), `communitiesConnected` (distinct other neighbor communities), and participation coefficient `1 − Σ_c (k_ic/k_i)^2` using unweighted distinct-neighbor degree; degree zero has coefficient zero. These are **partition-dependent** measures: a different LPA assignment changes them. A high coefficient at low degree is weak evidence of a broad bridge and must be shown beside degree. They are not betweenness centrality and do not prove graph articulation. Optional sampled betweenness was declined for 6D+6E.

Join both edge endpoints to community membership and aggregate by `(window, researcherId, neighborCommunityId)`, then by researcher. Both joins and both groupBy stages shuffle; hash-partition by window and researcher. Reuse cached membership and edges; no new checkpoint. No graph rows on the driver. Assert zero-degree coefficient zero, coefficient in [0,1] subject to floating tolerance, and cross-community degree no greater than total degree. Persist `missingCommunityMembership` and `bridgeResearchers` counters. Invalid bridge values fail the run and retain a hard-failure diagnostic; there is no separate invalid-bridge-value counter.

## Job 8 — K-core

**Inputs and versions.** Job 2 simple graph and Job 3's active-researcher intermediate, Spark version. **Outputs.** Coreness in finalized `ResearcherMetricsDetail` rows at `metrics/type=researcher_collaboration/window=.../run_id=.../`. The `metrics/type=kcore/window=.../run_id=.../` path is a materialized view of the same complete record keyed by `(windowId, researcherId)`; there is no separate k-core wire record in 6B.

Initialize each node to its unweighted degree. Iteratively set `core(v) = min(current core(v), H(neighbor cores))`, with distributed window operations to find the largest h for which at least h neighbors have core ≥ h. Continue until no values change and checkpoint at the configured interval. This h-index fixed point is exact coreness; isolates have 0. Partition by `(window, nodeId)`; neighbor joins, ranking/window and changed-value aggregation shuffle each iteration. Cache adjacency/current scores and release old scores. Driver stores only counts. Assert `0 ≤ coreness ≤ degree`, one row per active node, and convergence before `maxIterations`; count iterations and changed nodes.

## Job 9 — Temporal comparisons

**Inputs and versions.** Per-window jobs 3, 4, 6, 7 and 8, Spark version. **Outputs.** `TemporalChange` records under `metrics/type=temporal_changes/window=.../run_id=.../`.

Join consecutive **non-overlapping** periods only: `through-2009`, `2010-2014`, `2015-2019`, `2020-2026`. `TemporalChange.fromPresent` and `toPresent` explicitly represent whether a researcher occurs in each period. When both are true, report numeric deltas for distinct coauthors, average and maximum coauthors per paper, component size, and bridge measures. When one side is absent, all numeric deltas are absent, not a comparison against a fabricated zero; the presence flags and applicable previous/current community IDs remain. Largest-component entry/exit flags describe membership changes, including a researcher entering or leaving the population. Community continuity is best-match Jaccard overlap of member sets, ties by the smaller stable community ID, and is absent unless both sides exist. `all-years` and `since-2015` remain query windows but never enter deltas. Repartition by `(window, researcherId)` for metric joins and by community pair for overlap aggregation. Adjacent-period joins and community-intersection groupBy shuffle. Cache reusable membership only as measured; no iterative checkpoint. Driver stores period definitions and counts only. Config validation ensures compared windows are adjacent and non-overlapping. The persisted job counter is total `temporalChanges`; entry, exit and absent-side counts can be derived from each row's `fromPresent`/`toPresent` flags and are not separate counters.

## Job 10 — Deterministic semantic context

**Inputs and versions.** Jobs 1–9 outputs and source text references, Spark version. **Outputs.** `SemanticSummary` researcher-profile, community, selected collaboration-path and paper rows at `semantic-summaries/window=.../run_id=.../`.

Templates render only computed or source-backed fields. Every stated number and fact carries a `SummarySourceRef(table, rowKey, field)`; paper summaries point to abstract text IDs rather than copying full abstracts. Each `SemanticSummary` stores its `policyVersion`. `StableIds.sparkSemanticSummaryId(entityId, policyVersion, windowId, summaryType, text)` supplies each summary ID through `chunkOrProfileId`, with `sourceVersion` set to `s"$policyVersion:$windowId"`. The window binding gives identical text for one entity distinct IDs in different windows, while retaining a chunk/profile ID that evidence consumers can parse. There is no live LLM call. Join metrics/context by window and stable entity ID; distribute by `(window, entityId, summaryType)`. Context and metric joins and selected-member aggregation shuffle. Only small static templates may broadcast. Persist reused metric inputs if useful; no iterative checkpoint. Driver holds templates, not summary rows. Templates construct numbers directly from the referenced source fields, and module/independent tests resolve the cited keys and compare rendered values. Export validates the core summary record. The persisted job counter is total `semanticSummaries`; there are no separate missing-reference or skipped-summary counters. Required-field/schema failures fail validation rather than being presented as skipped rows.

## Job 11 — Parquet export, manifests and run gate

**Inputs and versions.** Validated domain-v1 and Spark-analytics-v1 outputs of jobs 1–10, plus both source manifests and the Spark config fingerprint. **Outputs.** Partitioned Parquet, a `RunManifest` binding the run, `SparkCounter` rows and `LoadManifest` handoffs. The relative layout is:

```text
nodes/type={researcher,author_mention,work,venue,institution,topic}/run_id=.../
edges/type={authored,resolves_to,coauthored_with,coauthored_with_support,published_in,affiliated_with,has_topic}/run_id=.../
metrics/type={researcher_collaboration,components,communities,cross_community_edges,bridges,kcore,temporal_changes,path_length_estimate}/window=.../run_id=.../
path-evidence/window=.../run_id=.../
semantic-summaries/window=.../run_id=.../
integrity/run_id=.../
run-manifest.json  counters.json  plans/  event-log-summary.json
load-manifests/{neptune,dynamodb,s3vectors,s3}.json
```

Each Parquet table uses the displayed partition columns plus its stable primary key for deterministic within-partition ordering. Do not force all rows into one file. Repartition to the table's partition/key distribution before writing; coalesce only if measured partition sizes justify it and without creating a driver-sized single partition. Sorting, repartitioning and content-hash aggregation are shuffle boundaries. No graph table is collected for hashing or manifest generation; compute sorted-row digests as distributed aggregates with an order-independent final combination defined by the implementation. The driver may hold the small manifests, counts and final digest scalars.

The run manifest binds input run IDs and manifest hashes, source snapshots, ER policy and hash, Spark config fingerprint, identity/representative versions, code version, windows, seeds, Spark and Java versions. An existing different output must not be overwritten; an identical completed run may be reused. Each proposed load manifest names logical dataset, paths, format, schema version, row count, key/partition columns, sorted-row content hash, run ID, windows, and future loader owner. Neptune mapping includes labels/types and ID property; DynamoDB proposes partition/sort keys for metric lookups and run state; S3 Vectors names summary documents and metadata; S3 carries Parquet/support data. These are Phase 7 loader proposals, not store writes. Counters and integrity failures are retained even on a hard-invariant failure; successful completion is marked only after all validated outputs and manifests exist.

## Verification boundary

The 6B deliverable was the design and core contracts/examples. Jobs 1–8 now have implementation and bounded local tests; jobs 9–11, the publishing CLI, the source-distance estimate and the JSON event-log summarizer are now included in 6F+6G. G1 provides hand-checked edges, P/C/T/A/M/W, components, paths and coreness; further fixtures cover LPA, star, K4, path, empty/single-node and missing-year behavior. Each implementing subphase runs its own module and independent tests plus the JDK 17 `sbt check`, retains actual evidence, and reports limitations. The live bounded EMR check moved to Phase 15 under the shortened Phase 6 schedule.

## 6D+6E implementation notes (jobs 3–8)

`Phase6DEJobs.build(spark, config, phase6cResult, lineage, runId)` consumes the completed 6C membership, edge and support tables. It returns distributed tables for detailed metrics, component membership and summaries, coreness, selected paths, community membership and summaries, cross-community edges, bridges, a typed path-length-estimate table, and named counters. The table shapes follow the additive `scholarchain.spark-analytics.v1` core records. `Phase6Main` publishes these outputs together with jobs 9–11 and the final manifests; `Phase6CMain` remains the historical jobs 1–2-only smoke interface.

The full CLI derives `codeVersion` from SHA-256 of the sorted Spark and core production class bytes (or the complete code-source JAR bytes under `spark-submit`). Class paths and timestamps are excluded. Any compiled semantic change changes the run ID, without relying on a manually maintained version string. The original completed 6C smoke outputs remain historical. The full pipeline records a valid core `RunManifest` in `run-manifest.json`; its original Hadoop `datasetSnapshots` are retained. `run-metadata.json` binds Hadoop/ER manifest hashes, ER policy, logical and physical config fingerprints, identity/representative/graph policies, windows, seed, Java/Spark versions, code fingerprint, output table counts and hashes. `_SCHOLARCHAIN_SPARK_COMPLETE` contains SHA-256 of `run-manifest.json` bytes, LF, and `run-metadata.json` bytes, plus LF. Component/community memberships and summaries use separate `components`/`component_summaries` and `communities`/`community_summaries` metric types. Integrity violations and reader rejects have separate `integrity/violations` and `integrity/rejects` datasets. Coauthor edges/support share their `run_id` directory across windows; each row retains its `windowId`, window-bound edge ID and context. Empty datasets have schema-bearing empty Parquet files, without synthetic rows.

All four `load-manifests/<store>.json` files contain arrays of core `LoadManifest` records, one per proposed logical dataset. They are storage-engineer proposals, with no store writes or embeddings. The S3 manifest includes every dataset; Neptune excludes the source projection and requires a Phase 7 decision for yearless edge mapping. DynamoDB key choices and S3 Vectors text/metadata mapping are explicit proposals. Every non-reject output row is checked on Spark executors against its core validator, except the documented source projection which is checked against its explicit source/context shape. Summary references use actual exported table names and stable row keys. Paper references preserve source years and abstract IDs; paper titles may be bounded to 900 characters, with no abstract text copied.

Logical content hashes use versioned `sha256-fixed-256-shard-sorted-row-json-merkle-v1`: top-level fields are sorted by name, explicit nulls remain, the physical `run_id` duplicate is excluded, and rows are assigned to a fixed shard by their row-JSON SHA prefix. Each executor sorts full row JSON in its shard and hashes the LF-joined sequence. The driver receives at most 256 `(shard,rowCount,digest)` values and hashes their sorted sequence with the method version. Duplicate rows affect both counts and digests. This is a deterministic Merkle content hash over sorted logical rows, independent of partition count and Parquet part names; it is not SHA-256 of concatenated Parquet files. Shard aggregation retains its local sorted rows in executor memory; the bounded Phase 6 slice is the measured scale, and larger runs must size partitions/shards accordingly. Writers hash-partition on directory columns plus primary keys and sort each final partition by primary key and full-row tie breaker. They do not funnel a global run into one partition.

Job 9 joins only adjacent comparison windows. Best Jaccard is evaluated from each previous community against intersecting current communities, selecting greatest overlap and then smallest current community ID; the row retains its actual current community as well. Entry/exit deltas remain absent. Job 10's researcher, community, path and paper templates stay below 1,200 characters, bind every stated fact/number to an exported source field, and use window/policy-bound core profile IDs. `Phase6Context` supplies one ordered explicit nested schema for jobs 1–11. The remaining Java-friendly UDFs call core stable-ID/validation functions that cannot be expressed faithfully as Spark built-ins; context construction itself uses literals and the shared schema. No typed Dataset encoder is used.

Event logs are uncompressed Spark JSON under the local output root's `.event-logs` directory. The streaming summarizer retains per-stage numbers only and can be replayed with `Phase6EventLog EVENT_DIRECTORY OUTPUT_JSON`. Failed tasks include retries; per-stage attempt IDs distinguish retry attempts. Event durations and physical plan text are operational evidence, not part of logical table hashes. A deterministic replay compares every table's row count and content hash and verifies every output record; it does not compare timing or part-file names. The real-data run's measured counts, limitations and LPA convergence are reported by the coordinator under `docs/agent-runs/phase-06/evidence/6fg/`.

## Phase 7A Neptune CSV handoff

New full-pipeline runs additionally invoke `Phase7NeptuneExport` after the unchanged Parquet handoff. Neptune's [documented bulk formats](https://docs.aws.amazon.com/neptune/latest/userguide/bulk-load-tutorial-format.html) do not include Parquet. The [openCypher format](https://docs.aws.amazon.com/neptune/latest/userguide/bulk-load-tutorial-format-opencypher.html) requires separate UTF-8 node/relationship CSV files, RFC4180 quoting, and the case-sensitive system headers below (checked 2026-10-22).

| Output relative to export root | Contents |
|---|---|
| `neptune-opencypher-csv/data/nodes/part-*.csv` | `:ID` from `nodeId`, `:LABEL` from `nodeClass`, display `label:String`, schema version, JSON strings preserving NamedText properties, provenance and Spark context |
| `neptune-opencypher-csv/data/graph-edges/part-*.csv` | `:ID` from `edgeId`, `:START_ID`/`:END_ID` from `fromId`/`toId`, `:TYPE` from `edgeType`, policy/schema version, source-evidence/properties/provenance/context JSON strings |
| `neptune-opencypher-csv/data/coauthor-edges/part-*.csv` | Exact Spark edge ID and endpoint IDs; `COAUTHORED_WITH`; typed `jointPublicationCount:Long`, first/last/window years as `Int`; window ID, representative-work JSON, context JSON, evidence-table/edge pointers |
| `load-manifests/neptune-opencypher-csv.json` | Versioned sidecar: run ID, `format=opencypher`, `userProvidedEdgeIds=true`, exact loader prefix, CSV dataset column lists/counts/logical hashes, original Parquet table hashes/counts/keys and support mapping |
| `edges/type=coauthored_with_support/` | Existing authoritative Parquet support, retained outside the Neptune loader prefix |

Only `neptune-opencypher-csv/data/` is a Neptune load source. The sidecar and support Parquet must remain outside that prefix. Each distributed CSV partition has its own header; Spark-generated success/checksum markers are removed only from the new writer's directories. No graph-sized data reaches the driver. Spark repartitions and sorts by the exact ID. An executor-side CSV encoder doubles quotes and preserves embedded CR/LF bytes; a minimal Spark text-writer wrapper emits one header per physical file (including empty output) and UTF-8 with CRLF record separators. This avoids the standard Spark CSV writer normalizing embedded CRLF into CRCRLF. These headers and the original IDs are never rewritten into another ID space. No synthetic context nodes or `SUPPORTED_BY` IDs are introduced when absent from Spark output.

An edge's `evidenceTable:String` is `edges/type=coauthored_with_support`; `evidenceEdgeId:String` is the unchanged Spark edge ID. Resolve the relative table path against the export root (ordinary S3 after upload) and select all support rows for that edge. The unique row key is the compound pair `(edgeId, workId)`, recorded as two columns rather than a delimiter-concatenated string. This preserves multiple works supporting one edge without collisions. Export validation rejects duplicate node/relationship IDs, absent endpoints, missing supporting Work nodes, duplicate support pairs, orphan support rows, and a support-row count different from `jointPublicationCount`, before writing any CSV. It uses distributed joins/aggregations and bounded existence checks.

Unknown first/last collaboration years and unbounded window years become empty numeric cells, so Neptune omits those properties; no dates are fabricated and the frozen numeric-window domain contract is unchanged. NamedText properties remain losslessly available in `propertiesJson:String` rather than being dynamically expanded into potentially invalid CSV column names. Source `provenanceJson:String` and/or `contextJson:String` retain lineage. Existing Parquet tables, their ID formulas, and the four historical proposal manifests keep their existing shapes. The additional sidecar is the concrete CSV contract for the later storage loader; no AWS loader or reader executes here.

The new compiled export changes the code fingerprint and therefore future full-pipeline run IDs. Previously completed runs are not reopened or modified. Phase 7A validates bounded Spark-shaped fixtures; it does not claim a fresh real-data replay or live Neptune acceptance. The local NIO export-root limitation is inherited from `Phase6Export`; cluster/object-store publication remains a later gate.


## Phase 12 offline readiness tools

`Phase12Readiness` is an additive operational CLI. It changes no existing Phase 6 readers,
ID formulas, provenance, completion markers or exports, and performs no AWS request.
The resources `phase12/g1-dblp.xml` and `phase12/empty.jsonl` are explicitly synthetic inputs:
nine DBLP-shaped G1 works with A–J test labels, including repeated A in w9 and solo J in w8.
Use the unchanged Hadoop preparation and offline (`--llm-mode disabled`) Phase 5 pipeline to
produce real completed upstream runs. Do not manufacture completion markers or replace real
data with a claimed G1 run. This DBLP-only topology does not test cross-source duplicate merging.

Build one current `sparkJobJar` using JDK 17. Use that exact JAR for both local and eventual
remote `Phase6Main` invocations and for the comparison command. Copy the completed upstream
files byte-for-byte; only deployment paths, checkpoints, output roots and shuffle counts may
change in the Spark configuration. Its logical settings must remain equal. The same JAR and
upstream/logical bindings produce the same run ID, including nested `context.runId`; there is
no provenance normalization in this tool.

Select this entry point with `spark-submit --class edu.uic.cs441.scholarchain.spark.Phase12Readiness`
or an equivalent Java invocation with the same job JAR and the selected runtime dependencies.
Positional commands are:

```text
probe SHARED_ABSOLUTE_DIRECTORY OUTPUT_JSON local|distributed
compare LEFT_COMPLETED_SPARK_RUN RIGHT_COMPLETED_SPARK_RUN OUTPUT_JSON
```

Paths must be absolute and normalized, with existing non-symlink parent directories. Outputs
are created exclusively, never overwritten. Probe creates a new random exchange directory
and retains it on success or failure; no evidence cleanup is automatic. The probe observes
Spark, Scala standard-library, reflection and Scala 3 class origins, class-byte SHA256 and
code-source JAR SHA256 on the driver and an actual task. Spark and Scala standard-library
runtime versions are observed directly. Reflection/Scala 3 runtime versions are explicitly
null when unavailable; package implementation versions may also be null in the merged job
JAR. The build owner must retain resolved artifact versions and their matching class hashes
before claiming exact version alignment. Job-JAR filenames or expected pins are not measured
component versions.

The task reads a unique driver token, creates its own exclusive proof file at the same absolute
path, and the driver verifies that exact proof. `distributed` additionally refuses executor ID
`driver`, unavailable identity or the same host/PID as the driver. `local` records the actual
result without upgrading it to distributed evidence. Neither a local task nor a distinct local
worker JVM proves that EMR nodes share a mount. `cloudCompatibilityVerified` remains false.

The proposed unchanged-application filesystem strategy requires a reviewed shared POSIX mount
at the identical absolute path on driver and executors and Hadoop `fs.defaultFS=file:///`.
The probe checks that default and bidirectional visibility, but the deployment must establish
the mount, permissions, quotas, encryption and failure behavior. Bare paths under EMR's default
HDFS, or separate executor-local `file:///` directories, are insufficient. No such mount is
provisioned here; S3 is not automatically a Java NIO shared filesystem.

Comparison checks both completion markers and exact semantic metadata, requires the current
code fingerprint to match the runs, and requires the exact 28-table inventory. It reads actual
Parquet, verifies schemas, recomputes every count and existing logical content hash, compares
full row multisets in both directions (including `run_id` and nested provenance), and refuses
stored-hash/count mismatches. It does not compare physical part filenames or operational event
times. A passing same-machine comparison is local readiness evidence only; later cloud runtime,
shared filesystem, independent deadline, spending and teardown gates remain open.
