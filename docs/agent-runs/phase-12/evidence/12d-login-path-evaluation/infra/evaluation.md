## Evidence and limits

1. [CLI sign-in guide](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html) describes browser authentication, temporary credentials and attaching login permission to a user, group or role. The [CLI login reference](https://docs.aws.amazon.com/cli/latest/reference/login/) explicitly illustrates an assumed-role ARN. Installed CLI 2.35.4's local help has that same assumed-role example. These establish supported principal types, not successful use of the proposed account identity.

2. [IAM console switching](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_switch-role-console.html) says original sign-in credentials authorize each switch and root cannot switch. [MFA API guidance](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_mfa_configure-api-require.html) puts MFA enforcement at role assumption; resulting role credentials do not carry MFA context for subsequent per-action MFA tests. Therefore candidate B keeps MFA on the role's trust/caller boundary and does not assume downstream token MFA inheritance. It must not add a role-wide per-action MFA condition that would reject the resulting role session. This explanation derives a candidate flow from documented components; the composition remains live-unverified.

3. [STS comparison](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_sts-comparison.html) permits an IAM user or role with existing temporary credentials to call `AssumeRole` and lists MFA support. [AssumeRole API](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html) accepts device serial and TOTP. Installed CLI source can resolve a source profile through `LoginProvider`, pass `mfa_serial` as `SerialNumber`, prompt via its MFA prompter, and include `TokenCode`. This supports candidate A without an IAM access key, but does not prove Sign-In-issued credentials satisfy every relevant live STS/caller-policy condition. A TOTP must never appear in a command argument, evidence, shell history or agent message.

4. [Global condition keys](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html) documents `aws:SignInSessionArn` for OAuth-origin requests separately from `aws:MultiFactorAuthPresent`. The former correlates a sign-in session; it is not an MFA claim and is not a substitute for the latter. The pages inspected do not establish MFA-context inheritance from `aws login` to a subsequent IAM-user `AssumeRole`. Retain that uncertainty rather than silently replace the strict trust condition.

5. [SignInLocalDevelopmentAccess](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/SignInLocalDevelopmentAccess.html), current v3, grants **both** `signin:AuthorizeOAuth2Access` and `signin:CreateOAuth2Token`. Earlier suggestions of a token-only grant are incomplete. The [Sign-In authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_signin.html) lists the same-device resource `arn:aws:signin:<region>:<account>:oauth2/public-client/localhost` for both actions. A future amendment should render a separate two-action statement on that exact account/region/client ARN, with independent feature assertions and no global managed-policy wildcard grant. Do not add account-level console authorization policies or new Sign-In administrative actions. Live action/resource enforcement remains unverified.

6. Installed CLI uses logical client IDs ending `devtools/same-device` and `devtools/cross-device`. These are request `clientId` values, **not IAM Resource ARNs**. They do not independently show that documented localhost resource scoping is wrong. Candidate B proposes same-device login only; no remote fallback or additional client grant is implied.

7. Pinned provider 6.44.0 `go.mod` uses Go SDK config 1.32.17, credentials 1.19.16 and aws-sdk-go-base beta.72. The matching SDK has `resolveLoginCredentials` and a login credentials provider that reads the SDK/CLI-managed cache and refreshes temporary credentials. Its cache path is derived from the login session string, without a user-only ARN restriction in the inspected helper. This gives source-based compatibility evidence for candidate B. No cache was opened and no provider credential resolution was executed.

8. The pinned SDK rejects an MFA role profile when a serial number is set but no token callback exists. The reviewed provider base credentials/config/load-options source does not supply an interactive MFA callback. Do not claim Terraform automatically prompts like the CLI. Candidate A would require a separately reviewed process-credential profile using the CLI's MFA-aware role resolver. [External process documentation](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sourcing-external.html) requires protecting supporting files and keeping credentials out of stderr/logs. That bridge is not selected or installed here.
