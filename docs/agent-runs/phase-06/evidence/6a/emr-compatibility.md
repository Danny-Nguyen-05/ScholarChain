# EMR Spark compatibility research for 6A

Owner: `infra-engineer`, native task `/root/infra_6a` (read-only research; no AWS account calls). This memo records published runtime facts and candidate investigations. It is not deployment approval or a successful EMR run.

## Published runtime versions

The [AWS EMR 7.x application version table](https://docs.aws.amazon.com/emr/latest/ReleaseGuide/emr-release-app-versions-7.x.html) lists Spark 3.5.x releases with Scala 2.12: EMR 7.0–7.2 use Scala 2.12.17; EMR 7.3–7.14 use Scala 2.12.18. EMR 7.8 has Spark 3.5.4-amzn-0 and Scala 2.12.18. The [EMR 7.8 release page](https://docs.aws.amazon.com/emr/latest/ReleaseGuide/emr-780-release.html) lists Corretto 17 as Spark's default Java runtime. The [EMR 7.0](https://docs.aws.amazon.com/emr/latest/ReleaseGuide/emr-700-release.html) and [7.14](https://docs.aws.amazon.com/emr/latest/ReleaseGuide/emr-7140-release.html) pages also list the supported Java runtimes for their releases.

Repository `project/Versions.scala` pins Scala 3.3.4 and Spark 3.5.4; `project/Dependencies.scala` requests `spark-sql_2.13` on the Provided classpath. [Scala's binary compatibility guide](https://docs.scala-lang.org/overviews/core/binary-compatibility-of-scala-releases.html) describes Scala 3 interoperability with Scala 2.13 libraries, not Scala 2.12 libraries. [Spark's 3.5 documentation](https://spark.apache.org/docs/3.5.2/) says the application must use the same Scala binary version as Spark. Therefore stock EMR 7.x is **not demonstrated binary compatible** with this job. The use of Java/DataFrame entry points narrows the API surface but does not establish runtime linkage. No EMR job was run.

## Scala 2.13 patch alignment for a custom Spark runtime — 6A repair round 1

Read-only `infra-engineer` research found that the [upstream Spark 3.5.4 Scala-2.13 build profile](https://raw.githubusercontent.com/apache/spark/v3.5.4/pom.xml#L3625-L3630) pins Scala **2.13.8**. The existing local job JAR's `library.properties`, read with `unzip -p modules/spark/target/spark-job_3-0.1.0-SNAPSHOT.jar library.properties`, reports `version.number=2.13.14`; `project/Versions.scala` pins `scala-reflect` 2.13.14. These are upstream-build and local-package observations, **not** an inventory of a proposed custom EMR image or distribution.

The [Scala binary compatibility policy](https://docs.scala-lang.org/overviews/core/binary-compatibility-of-scala-releases.html) states that Scala 2.13 patch releases through 2.13.18 retain both backward and forward binary compatibility, subject to exceptions for experimental or internal APIs and generated code. [Scala 3 interoperability guidance](https://docs.scala-lang.org/scala3/guides/migration/interoperability.html) explains its use of the Scala 2.13 standard library. Thus the 2.13.8-versus-2.13.14 patch difference alone does **not** establish a linkage failure. The stock EMR Scala **2.12 versus 2.13** mismatch remains the primary known incompatibility.

Before any 6H live run, after a human selects and authorizes a bounded fallback, inventory the exact Spark, `scala-library`, `scala-reflect`, `scala3-library` and Scala module JAR versions on **both driver and executors**. Compare them with the packaged job JAR and record effective class origins so duplicate Scala classes are visible. The preferred alignment is a coherent Spark 3.5.4 `_2.13` distribution with its tested Scala patch level and a job package built and verified against that same level; if the job must retain 2.13.14 while the selected distribution uses another 2.13 patch, require a documented compatibility proof on that exact pair. Then run a bounded startup and representative DataFrame/Parquet task and compare its rows with the local 6G result. Retain class origins, versions, logs, and any linkage or serialization error. Spark's `spark.driver.userClassPathFirst` and `spark.executor.userClassPathFirst` default to false and are marked experimental in the [Spark 3.5 configuration reference](https://spark.apache.org/docs/3.5.7/configuration.html#runtime-environment); changing classpath precedence is a contingency to test, not an assumed fix. Shading `scala.*` is likewise an unvalidated and risky inference because Spark and the job exchange Scala types. No custom runtime was selected or executed in this repair round.
