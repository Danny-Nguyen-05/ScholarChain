# Billing execution identity — offline policy drafts

This root renders policy JSON only. Source inspection establishes that it contains no resource, data source, provider configuration, module or provisioner. Its tests inspect the rendered documents and input validation; tests do not prove the absence of AWS resources. No identity, role, permission, budget or session is created. The actual operator ARN is deliberately unset. No credential, state, private recipient or prior real plan is needed.

The proposed deployment role is `scholarchain-billing-deployer`, configurable by a concrete role name. Its budget service permissions are five Budgets actions on one exact `arn:aws:budgets::<account>:budget/<name>` ARN. A separate candidate-B login document proposes two Sign-In authentication actions for this billing role only; neither document is attached. All account/budget inputs remain explicit; tests use synthetic identities. The caller and trust drafts remain null until a distinct same-account IAM user is supplied. `scholarchain-planner` is never trusted, elevated, given AssumeRole or repurposed.

## Permission audit — provider 6.44.0

Checked against [AWS Budgets service authorization](https://docs.aws.amazon.com/service-authorization/latest/reference/list_budgets.html), the versioned [budget implementation](https://github.com/hashicorp/terraform-provider-aws/blob/v6.44.0/internal/service/budgets/budget.go) and [tag implementation](https://github.com/hashicorp/terraform-provider-aws/blob/v6.44.0/internal/service/budgets/tags_gen.go) on October 31, 2026. API operation names are not IAM action names.

| Provider operation | IAM permission in this API-only draft | Reason |
| --- | --- | --- |
| CreateBudget, UpdateBudget | budgets:ModifyBudget | Budget amount, period, cost basis and initial creation |
| CreateNotification, DeleteNotification | budgets:ModifyBudget | Provider creates notifications with subscribers and reconciles changes by deletion/recreation |
| DescribeBudget, DescribeNotificationsForBudget, DescribeSubscribersForNotification | budgets:ViewBudget | Refresh and recipient/threshold readback |
| CreateBudget with ResourceTags; TagResource | budgets:TagResource | Five mandatory tags and changed values |
| ListTagsForResource | budgets:ListTagsForResource | Provider tag refresh/readback |
| UntagResource | budgets:UntagResource | Provider removes stale or changed tag keys during reconciliation; required governance tags must remain in reviewed configuration |
| DeleteBudget | budgets:ModifyBudget | Coarse IAM action also authorizes deletion; not a separate permission grant |

Every row is scoped to the exact budget ARN. No account-wide inventory, Cost Explorer API, report subscription, Budget Action, IAM, PassRole, EC2, EMR or model permission is included. `budgets:ModifyBudget` cannot distinguish authorized changes from deleting this budget, changing its recipient or raising its amount. The policy therefore cannot enforce the budget amount (USD 200 at creation, USD 25 after the Phase 14B modify) or the five tag values. Terraform validation, `prevent_destroy`, a reviewed plan and human approval are separate controls; none is an IAM deletion guarantee or a hard billing cutoff.

The service authorization operation table also lists legacy `aws-portal:ViewBilling`/`ModifyBilling`. Those actions cannot be scoped to a budget ARN. They are deliberately absent, rather than assigned an ineffective budget resource or broadened globally. [AWS migration guidance](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/migrate-granularaccess-whatis.html) says the aws-portal namespace reached end of standard support in July 2023, fine-grained permissions apply to accounts created after March 6, 2023, and Budgets API access is unaffected by console migration. This project's account was created in October 2026. The draft is for direct provider API use, not Billing-console navigation. This is a documentation-based authorization interpretation, not a live acceptance test. If exact-budget access fails, retain a sanitized diagnostic and stop for review; never add global portal access automatically. Console access, if later needed, needs a separate documented review.

## Trust and temporary credentials

The proposed contract is a concrete same-account IAM user distinct from root and planner, with registered MFA. Trust permits only that user's `sts:AssumeRole` with strict `Bool aws:MultiFactorAuthPresent=true`; no IfExists fallback. The caller policy permits only the exact billing role with the same condition. The caller draft is an explicit audit boundary even where same-account direct trust can independently authorize the named user. No grant is installed here.

[AWS MFA API guidance](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_mfa_configure-api-require.html) places MFA enforcement at role assumption. Candidate B is the selected **offline design**: the dedicated IAM operator signs into the console with MFA, switches to the billing role through this unchanged strict trust/caller boundary, then `aws login` selects that already-assumed billing-role console session in a dedicated profile. The pinned SDK can consume the role's native `login_session`; no second AssumeRole, `mfa_serial` profile or credential-process bridge is part of B. The [CLI login reference](https://docs.aws.amazon.com/cli/latest/reference/login/) includes assumed-role selection and the [console-switch guide](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_switch-role-console.html) describes original-user authorization. This composition is inferred from documented components, **not verified live**. No login has occurred.

Do not rely on an IAM-user OAuth session carrying MFA context into a later role assumption. [Condition-key documentation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html#condition-keys-multifactorauthpresent) distinguishes MFA context from OAuth session identity. `GetCallerIdentity` and CloudTrail metadata alone do not prove MFA or least privilege. Candidate A, permanent IAM keys and Identity Center remain separately reviewed alternatives, never automatic fallbacks. Never weaken the strict condition silently or invent credentials.

## Separate same-device login document — L1

`login_policy_json` is proposed **only for attachment to the billing role**, not the operator or planner. It allows exactly `signin:AuthorizeOAuth2Access` and `signin:CreateOAuth2Token` on `arn:aws:signin:<region>:<account>:oauth2/public-client/localhost`. `aws_region` defaults to `us-east-2` and validates concrete `xx-name-number` syntax; this rejects wildcards, not unknown regional availability. Account remains an explicit validated input. The condition pins `signin:OAuthClientId` to `arn:aws:signin:::devtools/same-device`. That logical OAuth client ID is distinct from the policy's account/region-specific IAM resource ARN. No remote-client, console resource, wildcard or Sign-In administrative action is granted.

The current [AWS managed policy](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/SignInLocalDevelopmentAccess.html) grants those two actions using wildcard public-client resources. This draft narrows that shipped pattern. The [authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_signin.html) also lists `console` resources, so exact-localhost scoping is a documentation-based inference requiring live acceptance. The extra client-ID condition may also cause a denial. **Stop for independent review on any denial**; never widen to console, `*`, another client, account or region automatically. No account-level console authorization policy is proposed. Adding this document does not alter or merge the exact five-action budget statement, trust or caller document.

## Future operator console prerequisites — L2

The user selected a **bootstrap-set console password without forced reset at first sign-in**, and an MFA device assigned by the separately authorized bootstrap actor before operator use. No `iam:ChangePassword` grant is authored. Passwords, MFA seeds/QR codes and one-time codes remain private with the human. The operator receives no MFA self-management grant. A later need to reset/change the password or manage MFA must go through the authorized bootstrap actor or a separately reviewed permission decision; this draft supplies no IAM self-service. Actual operator name/ARN, password, MFA device and setup are not established here. No console setup is authorized by selecting these documentation defaults.

## Session expiry and fail-closed handling — L3

The [CLI guide](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html) describes temporary credentials and refresh bounded by the principal's session duration, up to 12 hours. The console role session and proposed one-hour role maximum can shorten that; the complete refresh lifetime is unverified. If authentication expires mid-plan, stop and mark that attempt failed. Do not accept or reuse partial plan output. Under the separately authorized authentication window, the human reauthenticates only the dedicated billing-role profile, verifies the exact non-root/non-planner role, then reruns a fresh plan with a new checksum and the required review. Never fall back to root, planner, candidate A, a permanent key or Identity Center automatically. No cache, token or private profile content should be exposed. Session expiry and refresh do not stop billable resources.

For a future role, propose `max_session_duration=3600` seconds (IAM's minimum configurable maximum); request a shorter bounded STS session if supported by the selected authentication path. These durations are proposals and are not enforced by this output-only root. MFA-protected AssumeRole sessions and session expiry do not impose an AWS resource spending timeout.

## Establishment strategy — human choice still required

1. Preferred Terraform-first route: the human supplies an already authorized, non-root privileged bootstrap identity. A separately authored and reviewed Terraform IAM bootstrap would install only the named operator/role/policy/trust arrangement, with a fresh plan and human-written security-change approval. Such an identity has not been confirmed. This policy-only root cannot install its own permissions.
2. If root plus the read-only planner are the only available identities, strict Terraform-only bootstrap is blocked. Proposed exception for explicit human consideration: a one-time **human-performed account access bootstrap** using the MFA-protected root console to establish a new dedicated console operator, MFA, and the single billing role with the reviewed exact trust, execution, caller and separate role-login documents. No root access keys, no planner changes, no broad AdministratorAccess, no Organizations/Identity Center enablement and no project budget creation in that console step. The human would record the exact resources, session/login method and limits in their own approval. Later Terraform ownership/adoption of the IAM resources needs its own reviewed procedure and authorization; no ad hoc import or duplicate ownership. This is a proposed deviation from Terraform-only authorship, not an approved exception or instructions to execute now.
3. Stop until the human chooses a route, supplies the actual operator identity and authorizes the corresponding bounded IAM-establishment work order. A rejected/unworkable exception leaves the route blocked; it does not permit root-run Terraform. IAM provisioning permissions, any adoption procedure, credential setup and actual grants remain future reviewed work. The billing execution role itself receives no IAM provisioning permissions.
