# Pre-spend billing bootstrap — local preparation

This independent root defines one account-wide **USD 25 before-credit** cost budget (the professor's total course cap, Phase 14B replan) with three actual-spend alerts at fixed dollar amounts: USD 10, 15 and 20 (`ABSOLUTE_VALUE`, `ACTUAL`, `GREATER_THAN`). History: Phase 12D created this budget at USD 200 with 50/80/100 percent alerts (USD 100/160/200) through a protected copy of this root and the create-only wrapper in `scripts/billing`; the USD 25 values here are applied to that live budget only by the reviewed in-place **modify** path described under "Phase 14B" below. Earlier dated planning status is retained in [the billing-plan evidence](../../../docs/agent-runs/phase-12/evidence/12d-billing-plan/). `enable_budget` is false by default. Changing it is configuration, not approval to apply. Standard notifications are monitoring; they do not stop resources or impose a dollar cap.

## Phase 14B: USD 25 and three dollar alerts

Changed in this root (and nothing else): `budget_limit_usd` default and exact-equality validation 200 to 25 (so the superseded 200, and any other amount, fails validation), and the `notification` set from `[50, 80, 100]` / `PERCENTAGE` to `[10, 15, 20]` / `ABSOLUTE_VALUE`. Subscriber wiring is untouched (the private `budget_notification_emails` input, never committed). The CUSTOM period (2026-10-01 to 2027-01-01) and the five tags, including the derived `expiration_date` 2027-01-01, are unchanged: the period still covers the November session and final reconciliation, and a tag or period change would only add risk to an in-place update. Because the Phase 12D input file `approved-public-inputs.tfvars.json` carries `budget_limit_usd` 200, the modify uses a separate reviewed inputs file (`scripts/billing/modify-public-inputs.template.json`, rendered privately with the account ID into `approved-public-inputs.modify.tfvars.json`; the repository never holds the ID); the original file stays untouched and pinned.

**Replacement or in-place?** In place. `aws_budgets_budget` declares `notification` as an inline, repeatable block and `limit_amount`, `threshold` and `threshold_type` as ordinary arguments ([provider 6.44.0 resource documentation](https://registry.terraform.io/providers/hashicorp/aws/6.44.0/docs/resources/budgets_budget), read through the Terraform registry on 2026-11-08); the identity arguments (`name`, `account_id`, the period) are unchanged, so Terraform plans one `update in-place`. Per the provider audit in [billing execution](../billing-execution/README.md) the alerts are reconciled with Budgets `DeleteNotification`/`CreateNotification` calls inside that update, covered by the same `budgets:ModifyBudget` permission, so the existing execution policy needs no change. This is documentation-based; the saved plan produced by the human is the proof, and the wrapper refuses any plan whose only change is not an in-place update of this one resource. Even a replacement could not be planned, because the resource has `prevent_destroy`.

The mock tests assert the new shape (amount 25, exactly three notifications, every one `ACTUAL` + `ABSOLUTE_VALUE` + `GREATER_THAN`, thresholds `{10, 15, 20}`, no `PERCENTAGE`, no `FORECASTED`, none of 50/80/100, every threshold below the amount) and reject 200, 24, 26, 0 and 400. The exact human procedure (config-copy refresh, saved plan, gate, wrapper `modify`, state backups, verification and a realistic rollback statement) is in [the billing wrapper README](../../../scripts/billing/README.md#phase-14b-reviewed-modify-of-the-live-budget-to-usd-25). Offline checks here: `init -backend=false -lockfile=readonly`, `fmt -check -recursive`, `validate`, `test` (12 runs).

Use a fixed `CUSTOM` period so October and November spending share the same ceiling. The human must supply explicit UTC start/end timestamps covering **all** project spending, including early spikes, delayed charges and retained evidence, rather than only the November deployment window. No service, region or tag filter is configured. Credits and refunds are excluded; taxes, support, usage and subscriptions are included with unblended/non-amortized costs. Discounts remain included in the normal billed-usage basis. This is conservative account-wide monitoring, not precise per-project attribution.

AWS deletes a budget and its notifications after its end date. Choose an end that covers the retention period and final billing reconciliation; review/extend it before expiration if required. Do not infer that the November 25 submission deadline ends storage spending. No date is selected or automatically approved here. Live acceptance of the custom date range and alert delivery remains unverified.

The [AWS Budget API](https://docs.aws.amazon.com/aws-cost-management/latest/APIReference/API_budgets_Budget.html) documents `CUSTOM`, cost filters and time-period behavior. The [TimePeriod API](https://docs.aws.amazon.com/aws-cost-management/latest/APIReference/API_budgets_TimePeriod.html) documents expiration. Provider [6.44.0 resource documentation](https://registry.terraform.io/providers/hashicorp/aws/6.44.0/docs/resources/budgets_budget) and its [versioned implementation](https://github.com/hashicorp/terraform-provider-aws/blob/v6.44.0/internal/service/budgets/budget.go) support these fields. Checked during 12D preparation; documentation is not live proof.

The AWS Budget API marks **CostTypes as deprecated**. This pinned configuration still authors `include_credit=false` and `include_refund=false`, but mock plans cannot prove that the live service honors that accounting basis. After a separately approved apply, read back the exact budget's `CostTypes`, `TimePeriod`, amount and notifications using an approved identity and a recipient-free output projection. Require both `IncludeCredit=false` and `IncludeRefund=false`, as well as the expected tax/support and unblended settings, before accepting the monitor as the pre-spend gate. Check the configured basis in the Billing console as needed. If the service omits, changes or does not honor these fields, **stop before paid work** and route a `Metrics`/`FilterExpression` accounting alternative for independent review and human approval; do not silently switch to net costs or declare the before-credit gate passed.

The five required resource tags are applied directly to the budget. `resource_tags` supplies validated `course`, `project`, `environment` and `owner` values, defaulting to the human-selected `CS441`, `scholarchain`, `course` and `danny`. Their values must be nonblank and contain no email address. `expiration_date` is derived from the explicit budget end timestamp and therefore follows retention/final reconciliation, not the main stack's November 25 date. The date is a tag, not permission to delete anything. Extend both the budget period and derived tag through an approved change if retention continues. The mock test checks the actual budget resource's complete tag map with synthetic values different from those defaults, and checks a changed reconciliation end.

Supply `aws_account_id`, `aws_profile`, `aws_region`, a nonpersonal unique `budget_name`, `project_period_start_utc` and `project_period_end_utc`. The AWS date format is `YYYY-MM-DD_HH:MM` UTC. The exact notification recipient is private: supply `TF_VAR_budget_notification_emails` interactively without shell history, or an ignored `*.local.tfvars` outside Git. Do not echo it or commit it. Do not read credential files, root keys or session caches. Saved plans and state may contain the recipient even though the input is sensitive; keep both outside Git and evidence and avoid unredacted Terraform logs.

Tests use only `mock_provider "aws"` with `command = plan`; the address in the test is synthetic `example.invalid`. No account call, real plan, apply or credential lookup is authorized by this README. A real plan requires a refreshed, approved read-only identity and private inputs; keep its binary/JSON outside Git, retain only approved summaries and SHA-256. Applying requires independent review and a human-written approval of that exact plan and deployment identity. Verify the budget and all notification thresholds afterward before a paid run. Cost Explorer must be enabled by the human in the console; this root cannot activate it. Paid Cost Explorer API calls are outside this work order.

Use a **separate state** outside the repository, for example a dedicated protected working copy plus `TF_DATA_DIR` and an explicit local-state path. `TF_DATA_DIR` alone does not relocate state. Never copy the main course state or use the same backend key. The bootstrap is the sole owner of this account-wide budget. Keep the main course input `enable_budget_resource=false`; its currently authored monthly/tag-filtered foundation budget is not this cumulative monitor. A later migration requires an explicitly reviewed state/ownership procedure. Do not enable both roots for the same budget, import ad hoc, or delete an existing monitor to avoid a name conflict. `prevent_destroy=true` protects this monitor from routine cleanup; changing that protection requires its own human decision.

Before deployment, the separate non-root execution identity requires tagging permissions because this root always supplies the five resource tags. The complete provider-operation/IAM audit, modern API-only treatment of legacy non-scopable aws-portal actions, exact-budget policy and proposed MFA trust are documented in [billing execution preparation](../billing-execution/README.md). Those are uninstalled drafts; identity establishment and its credential workflow remain separate human gates. AWS maps the `CreateBudget` API to `budgets:ModifyBudget`; creating a tagged budget also requires `budgets:TagResource`. Refresh and tag readback require `budgets:ViewBudget` and `budgets:ListTagsForResource`; tag changes require `budgets:TagResource`, with `budgets:UntagResource` for removals. Review these IAM actions against the exact proposed budget ARN and the current [AWS Budget Service authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_budgets.html) (checked 2026-10-31); API operation names are not interchangeable with IAM action names. No permission is granted by this documentation. No IAM user, role, policy, attachment or broad administrator grant is authored or installed here. `scholarchain-planner` stays read-only. This bootstrap creates no report subscription, automated Budget Action, SNS topic or paid hourly cost data collection.
