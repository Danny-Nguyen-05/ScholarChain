# ScholarChain scripts

## `phase4-emr-smoke.sh`

Bounded EMR smoke for `HadoopPrepMain`: one `--once` run with `--execution-mode cluster` over the four sample paths under an existing S3 input prefix. Hadoop stays **Provided** on the cluster. The step does not ship a Hadoop client JAR.

The step uses `command-runner.jar` and `bash -c` on the cluster master. The job JAR is `hadoop-submit_*.jar` (module classes plus `lib/<dependency-bundle>.jar` for RunJar). Do not submit the thin JAR alone. Before `hadoop jar`, the step localizes that submit JAR, the dependency bundle, and the prep config into a fresh work directory under `${TMPDIR:-/tmp}`:

- `s3://`, `s3a://`, `s3n://`, and `hdfs://` sources are copied with `hadoop fs -copyToLocal`.
- Any other path is copied with `cp` when it is already a regular file on the master.

The driver exports `HADOOP_CLASSPATH` to the localized bundle. Tasks receive that same localized bundle through `-libjars` on the application arguments. `--config` is the localized local file, never the original remote URI. Dataset inputs (`--dblp`, `--openalex`, `--crossref`, `--orcid`) and `--output-root` stay remote `s3://` URIs. Sample data is not copied onto the master.

Required inputs (no defaults): EMR cluster id, AWS region, S3 input prefix, S3 output prefix (`s3://bucket/non-empty-key`), submit JAR (`SCHOLARCHAIN_HADOOP_SUBMIT_JAR` or `--jar`; `hadoop-submit_*.jar`), dependency bundle path (`SCHOLARCHAIN_HADOOP_DEPENDENCY_BUNDLE` or `--libjars`), and prep config path. `SCHOLARCHAIN_HADOOP_THIN_JAR` is a deprecated alias for the submit JAR value. Jar, bundle, and config may be cluster-visible remote URIs or master-local paths.

The step passes `--output-root` from `--output-prefix` (overrides config `outputRoot` on the cluster) and fixed snapshot/retrieval metadata for the overridden S3 sample paths. `maxLocalSampleRecords` in the prep config is documented in `--help` as a launch-level bound for the whole step, not a per-mapper cap.

The step also enforces an inclusive smoke ceiling on the prep config. A local regular `--config` file is checked before the EMR step is built; failure exits non-zero and does not print `aws emr add-steps`. The cluster `bash -c` body runs the same check after `copyToLocal` and before `hadoop jar`, so a remote config is checked on the master. Each ceiling field must be present as a JSON number. Missing or non-numeric fields fail closed. The master needs `python3` for that localized check. The loader's positive-value check still applies when the job starts.

- `maxLocalSampleRecords` <= 1000
- `reducerCount` <= 8
- `maxCandidateBlockSize` <= 256
- `maxCandidatePairsPerBlock` <= 4096
- `maxAuthorTeamSize` <= 64
- `maxRecordBytes` <= 8388608
- `maxXmlEntityExpansion` <= 8388608

The committed `scholarchain.hadoop-prep.v1.json` profile is inside this ceiling.

Default behavior is **dry-run**: it prints the exact `aws emr add-steps` command and exits without submitting a step and without invoking `hadoop` or `aws`. Pass `--execute` only after human approval.

# Phase 13 automation: check, package, plan, deploy, rollback, cleanup (Subphase 13A)

Source-controlled commands that reproduce validation, packaging, Terraform planning, deployment, rollback and cleanup from a clean checkout. In Phase 13A **nothing here has been run against a real AWS account**; `deploy.sh`, `rollback.sh` and `cleanup.sh` are dry-run only, and `plan.sh --execute` needs the user's approved profile. The smoke test, bounded pipeline, experiment runner and evidence archive are Subphase 13B (section "Subphase 13B" below); the same scripts are the ones the final README reproduction steps will cite.

Every script: `#!/usr/bin/env bash`, `set -euo pipefail`, `--help` (purpose, inputs, approval points, exit codes, evidence), no interactive prompts, greppable `STEP: <name>` markers and exactly one final `RESULT: <PASS|FAIL|DRY-RUN|REFUSED|PARTIAL> ...` line. This holds for bad usage too: an unknown flag or a flag without its value prints `STEP: start`, `STEP: usage` and one `RESULT: REFUSED step=usage reason=...` line and exits 2 (`sc_usage_exit` in `scripts/lib/common.sh`, used by all eleven scripts that parse options before `sc_init`); `--help` still exits 0. Every external command runs through `scripts/lib/timeout.py`, which starts it in a new process group and, on timeout, sends SIGTERM to the whole group, then SIGKILL after a grace period, and exits 124; it rejects a non-finite or non-positive `--seconds` (nan, inf, 0, negative) with exit 2 before any child starts. The Terraform version probe goes through it too. The cloud scripts (`plan`, `deploy`, `rollback`, `cleanup`) are **dry run by default**: they print each command as `DRY-RUN CMD: timeout=<s>s <command>` and run none of them.

## Redaction and retained output

Printed commands, all shown output, **retained logs** and the **timeout trace** (`SCHOLARCHAIN_TIMEOUT_LOG`) are redacted before anything is written or shown: the account ID becomes `<acct>` (ECR hosts print as `<acct>.dkr.ecr.<region>.amazonaws.com`), the values of environment variables whose names contain SECRET, TOKEN, PASSWORD, ACCESS_KEY, API_KEY, CREDENTIAL or PRIVATE_VARS, or that end in `_KEY` (so `SCHOLARCHAIN_SMOKE_API_KEY` is hidden by every script, not only `smoke-test.sh`), become `<redacted>`, and so do the path and every quoted string value of the private variable file named by `SCHOLARCHAIN_TF_PRIVATE_VARS` (registered by every script; the file is read only to build that list and is never printed). Raw subprocess output is never persisted: `scripts/lib/redact.py` filters it first, and `timeout.py` writes no trace line at all if it cannot load that filter. 12-digit runs bounded by letters or digits (inside a 64-hex checksum) are left alone.

## Prerequisites

- JDK 17 (the scripts apply the JDK 17 environment themselves: `JAVA_HOME` override, then `/usr/libexec/java_home -v 17`, then the configured Homebrew path; `java -version` must report 17), sbt, and `docs/agent-runs/phase-04/xml-repair-logback.xml` (sets `SBT_OPTS`).
- Terraform exactly **1.13.5** (tfenv on `PATH`, or `TERRAFORM_BIN`). Any other version is refused with exit 3 and the found version in the message.
- Docker with buildx (`package.sh`; without a reachable daemon it falls back to jars plus a static Dockerfile check and says so), `shellcheck`, `python3` (stdlib only), `git`, `shasum`, and the AWS CLI (only for `--execute` paths). `jq` is not used.
- `terraform init` (the `check.sh` terraform gate) downloads the pinned provider over the network; it makes no AWS API call and the AWS credential variables are unset for those commands.

## Scripts

| Script | Mode | What it does |
|---|---|---|
| `check.sh [--only G,...] [--skip G,...]` | real run, no cloud | gates `constitution`, `hooks`, `shell`, `python`, `terraform`, `script-tests`, `sbt` (in that order: the terraform gate's `init` installs the providers that the real-Terraform script tests need, so a clean checkout runs them instead of skipping them; in a default full run a skipped or missing `test_terraform_state_binding.RealStateBindingTests` or `test_terraform_r1.RouteOwnershipTest` **fails** the `script-tests` gate, and the gate reports `executed = Ran - method-level skips` and lists skipped classes separately); summary table; exits 4 if any gate fails; `RESULT: PARTIAL` with **exit 5** when gates were skipped by `--only/--skip` (never a pass); only a full default run that passes exits 0 |
| `package.sh [--require-images] [--require-runtime-archive]` | real run, no cloud | `sbt -batch packageRelease`; collects the Hadoop submit JAR, dependency bundle, Spark job JAR and service distribution; builds four `linux/amd64` images; architecture gate; verifies the G5 archive; writes `target/release/<commit>/release-manifest.json` |
| `plan.sh --env NAME` | dry run; `--execute` = real read-only plan | from a `git archive` of the commit (never the work tree), bound to the live local state: `aws sts get-caller-identity`, `terraform init`, `plan -out`, `show -json`, `show -no-color`; checks the saved plan's region, account, environment, project and image revision; writes the v2 provenance receipt (source tree hash, state identity) and the full private plan text; **never applies** |
| `deploy.sh --stage S --plan FILE` | dry run only in Phase 13 | verifies the approval record, pre-spend receipt and (except for `push`, which has no plan) the plan, receipt hash, state binding and source, then prints (or with `--execute` runs) exactly one stage: `base-apply`, `push`, `runtime-apply` or `cleanup-prepare`; the dry run runs no Terraform command beyond the version probe |
| `rollback.sh --env NAME ...` | dry run only in Phase 13 | policy 13-5 through plan.sh and deploy.sh; infrastructure rollback runs the current scripts against the previous commit's materialized source and, while the live state shows the runtime, carries the deployed image revision (`--deployed-manifest` or `--deployed-push-record`) so the running runtime is kept |
| `cleanup.sh --env NAME` | dry run only in Phase 13 | classifies the state under the preservation policy; refuses (`PREPARE-REQUIRED`) while a teardown resource is still deletion-protected; `--prepare` plans the protection release; lists the plan's actual destructive actions; destroys only with a token bound to the exact saved plan |

`check.sh` details. `constitution`: required constitution files exist and every tracked or new `*.json` parses (prefixes in `JSON_FIXTURE_EXCLUDES` are deliberate fixtures). `shell` and `hooks`: `bash -n` plus `shellcheck -x` with no suppressed findings. `python`: `python3 -I -X pycache_prefix=<tmp> -m py_compile` (no bytecode is written into the repo). `script-tests`: the **pinned** list `scripts/tests` and `scripts/phase12d-spike/tests` (one unittest discovery each, run through `scripts/lib/suite_run.py`, which keeps unittest's own report and adds a `SUITE-SUMMARY` line) plus each `scripts/billing/tests/test_*.py` in its own process (the three billing suites fail when loaded together by one `unittest discover` process, 28 failures on the unmodified base, and pass individually; `scripts/billing/tests/terraform_state_binding.py` is a helper, not a test file). The list cannot be replaced from the environment or the config; **an omitted suite fails the gate, and a suite or test file that executes zero tests (or has no `test_*.py` file at all) fails the gate**. **Counts (N4):** unittest's `Ran N` counts collected tests, and a class-level skip (a `SkipTest` in `setUpClass`) adds one skip but no test to it, so `Ran - skipped` undercounts after a class skip. The gate reports **executed = Ran minus the method-level skips**, the method skips and, separately, every skipped class (`SUITE-SKIPPED-CLASS`). **Required real-Terraform classes (N4):** `test_terraform_state_binding.RealStateBindingTests` (R1) and `test_terraform_r1.RouteOwnershipTest` are pinned in `check.sh`; in a **default full run** (no `--only` or `--skip`) each must execute at least one test and none may be skipped, so a missing provider directory fails the gate instead of passing silently (`SUITE-REQUIRED ... status=SKIPPED|MISSING`, `SUITE-REQUIRED-FAILED`). The `terraform` gate runs first for that reason (its `init` installs the providers). A partial run only warns, and is never a pass anyway. `sbt`: `sbt -batch check` under JDK 17 (timeout `TIMEOUT_SBT_CHECK_SECONDS`, about 13 minutes of work on the reference machine). `terraform`: `fmt -check -recursive`, then for each root with a `versions.tf` outside `modules/` (root, billing-bootstrap, billing-execution, deployer, `spikes/*`): `init -backend=false -input=false -lockfile=readonly` (so tracked `.terraform.lock.hcl` files are never rewritten; a changed lock file fails the gate), `validate`, and `test` where a `tests/` directory exists. Logs (redacted): `target/check-logs/<run-id>/`.

`package.sh` details. Images are built as `docker buildx build --platform linux/amd64 --provenance=false --sbom=false --build-arg MAIN_CLASS=<main> -t scholarchain-<service>:<tag> --load .`; `--provenance=false --sbom=false` stop buildx adding an attestation manifest so the loaded image is single-platform and its architecture is unambiguous. Tag = the full 40-hex commit SHA, plus `-dirty` on a dirty tree (`deploy.sh` refuses those). **Architecture gate:** (a) `docker image inspect` OS/architecture must equal `IMAGE_PLATFORM`; (b) `IMAGE_PLATFORM` must equal the ECS task `cpu_architecture` parsed from `infra/terraform/modules/runtime/compute.tf` (`X86_64` is `linux/amd64`, `ARM64` is `linux/arm64`, anything else fails). Check (b) always runs. The manifest records each image's local image ID and OS/arch; `deploy.sh --stage push` re-inspects the local tag and refuses if it no longer resolves to that ID. The Hadoop submit JAR embeds timestamps and is not byte-reproducible; its sha256 is of that build. Registry digests do not exist at build time; `deploy.sh` records them at push time.

## Plan outputs and the complete review path (plan.sh)

**Private run directory (R2).** Every run creates a **fresh** directory `<PLAN_DIR>/<run-id>` (`target/plans/<run-id>`, `mkdir` 0700, refused if it exists) for the materialized source, the Terraform data directory and, by default, every output. Files are 0600. Nothing is ever reused or overwritten: an explicit `--plan-out` / `--receipt` below `PLAN_DIR` is accepted only when **every** output path is absent beforehand (a leftover file, a live or dangling symlink at a derived name is refused, never followed), inside `PLAN_DIR` (no `..`, no symlinked component; an alias of the repository root itself is fine), reported ignored by `git check-ignore`, pairwise distinct (case aliases and a file used as the directory of another output are refused as collisions). The files themselves are opened with `O_CREAT|O_EXCL|O_NOFOLLOW` below an `O_NOFOLLOW` directory chain (`scripts/lib/safeio.py`, also used by `timeout.py --stdout-new`, the receipt writer, the deploy manifest and the cleanup evidence), never truncated. The one file Terraform itself creates (`-out`) is protected by the absence check and the fresh 0700 directory. `plan.sh` prints `PLAN-FILE: <path>` (the path to pass to `deploy.sh --plan`). Set `TF_PLUGIN_CACHE_DIR` so each fresh run directory does not download the providers again.

| File | Content |
|---|---|
| `<plan>` (`<env>-<commit>.tfplan` by default) | the saved plan binary |
| `<plan>.json` | raw `terraform show -json` (may hold variable values; never evidence) |
| `<plan>.txt` | the **complete** `terraform show -no-color` text of that exact saved plan |
| `<plan>.log` | the redacted `terraform init`/`plan` output |
| `<plan>.receipt.json` | provenance receipt (below); checksums, counts, state identity and the action list only |

**Source (R3).** The plan **always** runs from a `git archive` of the commit (HEAD, or `--source-commit`) extracted into `<run-dir>/source/<commit>` and made read-only, never from the work tree, so a Git-ignored `override.tf` / `*_override.tf` can never load, and an edited tracked file is not planned. The hash of the Terraform root tree is recorded as `source_tree_sha256`; `deploy.sh` re-materializes the commit and compares it.

**State (R1).** The root uses the **local** backend. Terraform would plan the materialized copy against a fresh, empty state, so the copy gets a generated `zz_scholarchain_state_binding.tf` (`backend "local" { path = "<abs live state>" }`, proven with real Terraform 1.13.5) pointing at `TERRAFORM_STATE_FILE` (`infra/terraform/terraform.tfstate`, pinned). The receipt records the state's `lineage`, `serial` and `sha256` (nothing else is read out of the state file; the identity is re-read after the plan and the run fails if it changed meanwhile). A missing state is refused unless `--expect-new-state` (a very first deployment; then an existing state is refused and the receipt records `{"present": false}`). A source that declares its own backend block is refused.

`--plan-out` and `--receipt` outside `PLAN_DIR` are refused (exit 3, before any command runs); the refusal happens before anything is written, so a name such as `course.plan` at the repository root (whose `.json` export no ignore rule covers) cannot leave sensitive JSON eligible for commit.

Review path, nothing truncated: the script prints `PLAN-TEXT: <path> sha256=<hash>` (read the full text locally; it is private and never shared), and the shareable action list `PLAN-ACTIONS-BEGIN count=N`, one `PLAN-ACTION: <actions> <address>` line per resource change that is not a no-op or a read, `PLAN-ACTIONS-END count=N`. Only addresses and action verbs appear (no attribute values, no variable values; a 12-digit run inside an address becomes `<acct>`); the same list is in the receipt. The `terraform plan` console text itself is not echoed on success. It then prints `PLAN-RECEIPT: <path> sha256=<hash>` and the candidate approval-record lines.

**Plan receipt** (`scholarchain.plan-receipt.v2`): `purpose` (`deploy-plan`, or `cleanup-prepare` from `cleanup.sh --prepare`), `plan_sha256`, `commit` (the commit of the Terraform source that was planned), `scripts_commit` (HEAD of the checkout whose scripts ran), `clean` (work tree clean when planned; an unreadable tree is recorded as not clean), `account_sha256` (never the raw ID), `region`, `env`, `planned_environment` and `planned_project` (read from the saved plan's own variables), `source_tree_sha256`, `state` (`present`, `lineage`, `serial`, `sha256`), `image_revision` (null when none), `terraform_version`, `created_utc`, `plan_json_sha256`, `plan_text_sha256`, the add/change/destroy/replace counts, the IAM and stateful-resource changes, and `actions`. Before writing it, `plan.sh` checks the saved plan's own provider region, `aws_account_id` variable (hashed), `environment`, `project` and `image_revision` variables against the inputs (the private tfvars file can override `environment`; the plan's own value is what counts) and exits 4 on any mismatch. The receipt's sha256 goes into the approval record (`APPROVED_RECEIPT_SHA256`), so a receipt edited after review is refused.

## Human approval points (plan Section 7.3)

1. **`deploy.sh --execute`**: the Phase 14 approval record and the pre-spend receipt it names (below), one per stage.
2. **`run-bounded-pipeline.sh --execute` and `run-experiment.sh --execute`**: an approval record naming the manifest or run configuration, budget, region, capacity, maximum runtime and teardown, plus a pre-spend receipt (keys and gates in "Subphase 13B" below).

## Approval record and account hash (deploy.sh)

`deploy.sh` reads `docs/agent-runs/phase-14/human-gate.md` (or `--approval FILE`). The human writes these lines, each **exactly once**, as `KEY=value` with no quotes and no spaces around `=`:

| Line | `base-apply`, `runtime-apply`, `cleanup-prepare` | `push` |
|---|---|---|
| `APPROVED_STAGE=<base-apply or push or runtime-apply or cleanup-prepare>` | required | required |
| `APPROVED_COMMIT=<40 lowercase hex>` | required | required (HEAD) |
| `APPROVED_ACCOUNT_SHA256=<64 lowercase hex>` | required | required |
| `APPROVED_REGION=<aws region, for example us-east-2>` | required | required |
| `APPROVED_ENVIRONMENT=<environment name, for example course>` | required | required |
| `APPROVED_PRESPEND_SHA256=<64 lowercase hex: sha256 of the pre-spend receipt file>` | required | required |
| `APPROVED_PLAN_SHA256=<64 lowercase hex>` | required | **refused if present** (a push names no plan) |
| `APPROVED_RECEIPT_SHA256=<64 lowercase hex: sha256 of the plan receipt the human reviewed>` | required | **refused if present** |

A missing file, or a missing, duplicate or malformed line (including uppercase hex, quotes, a CR line ending, an unknown stage), refuses with exit 3 and a `STEP:` marker naming the failed check. Other text in the file (prose, headings) is ignored, but **an unknown `APPROVED_*` key (for example a misspelt one) refuses** (`approval record has an unknown key ...`, exit 3): extra keys are never ignored. `plan.sh --execute` prints the plan-stage lines for the human to review and paste (the last two as placeholders); the scripts never write the record. `APPROVED_COMMIT` is the commit of the Terraform source being applied: HEAD normally, the previous commit for an infrastructure rollback. `deploy.sh` compares `--stage` with `APPROVED_STAGE` first (the stage decides which other lines are required), then the commit, region and `APPROVED_ENVIRONMENT` (which must equal the environment the scripts operate on, `NAME_PREFIX_ENVIRONMENT`).

`APPROVED_RECEIPT_SHA256` binds provenance to the approval: the receipt is copied once, its sha256 must equal the approved value, and only then are its fields (clean tree, commit, account, region, environment, planned environment and project, terraform version, image revision, source tree hash, state identity, purpose) trusted.

`APPROVED_ACCOUNT_SHA256` is the lowercase hex sha256 of the 12-digit account ID string with no trailing newline: `printf '%s' "$id" | shasum -a 256`. `deploy.sh --execute` obtains the ID with `aws sts get-caller-identity --query Account --output text`, hashes it the same way, compares it **before any mutating command**, and never prints the raw ID.

**Dirty-tree rule (exact).** `deploy.sh` parses `git status --porcelain=v1 -z --untracked-files=all` and refuses on any path other than the **literal configured** `APPROVAL_RECORD_PATH` (`docs/agent-runs/phase-14/human-gate.md`), compared as an exact string (never a git pathspec, so a file named `*` or `:(exclude)...` or `human-gate.md.bak` is dirty). The human writes the record after the plan and committing it would move HEAD away from `APPROVED_COMMIT`, so do not commit it before deploying. `--approval FILE` chooses which file is read but adds **no** exemption: an alternate in-repo record path makes the tree dirty unless git ignores it (for example under `target/`). No environment variable adds an exclusion, inherited `GIT_*` variables are removed, and a `git status` that fails or prints unparsable output **refuses** instead of reading as clean.

### Pre-spend receipt (plan Section 7.3a)

The human writes a JSON file (default `target/phase14/prespend-receipt.json`, git-ignored so it never makes the tree dirty; override with `--prespend FILE`, and `rollback.sh --prespend FILE` passes it through) and records its sha256 as `APPROVED_PRESPEND_SHA256`:

```json
{
  "schema": "scholarchain.prespend-receipt.v1",
  "monitoring_confirmed_active": true,
  "cost_snapshot_utc": "2026-11-05T12:00:00Z",
  "reported_spend_usd": 12.50,
  "unreported_usage_allowance_usd": 5.00,
  "reserves_usd": 40.00,
  "remaining_headroom_usd": 150.25
}
```

`monitoring_confirmed_active` must be the JSON boolean `true` (the budget alert and cost monitoring were confirmed active by the human); `cost_snapshot_utc` is `YYYY-MM-DDTHH:MM:SSZ`; the four `*_usd` fields are JSON numbers (not strings, booleans or null; no NaN or Infinity). Other keys are ignored. `deploy.sh` (and `rollback.sh` through it) refuses with exit 3, at step `prespend-receipt` and **before any aws, docker, apply or upload command**, when: the file is missing or not valid JSON; its sha256 differs from `APPROVED_PRESPEND_SHA256`; the snapshot is older than `PRESPEND_MAX_AGE_HOURS` (24) or in the future; monitoring is not `true`; `remaining_headroom_usd` is below `PRESPEND_MIN_HEADROOM_USD` (20 USD); or any of the four cost fields is missing, null or non-numeric (missing is never treated as zero). The receipt is copied once into a private directory before it is hashed and read.

**Re-verified before every paid operation (R7).** The same checks (copy hash, monitoring, freshness, headroom, numeric fields) run again immediately before **each** paid operation: the ECR login, every image push, every Terraform apply and the runtime archive upload. A receipt that was valid at the start but expired meanwhile stops the stage at that operation (`pre-spend receipt rejected before <operation>`; for example after a long base apply no upload follows). **Test-only clock:** `SCHOLARCHAIN_TEST_CLOCK_FILE` (a JSON object `{"default": "<UTC time>", "<operation>": "<UTC time>"}`, operations `initial`, `ecr-login`, `push-<service>`, `terraform-apply`, `archive-upload`) supplies the time, and is honoured **only** together with the announced test-only `SCHOLARCHAIN_CONFIG_FILE` (`CLOCK-OVERRIDE:` on stdout); with the real repository config it is ignored (`CLOCK-IGNORED:`). A malformed clock file fails closed.

## Deploy stages (deploy.sh)

Each Phase 14 step is a separate stage with its own approval record and its own fresh pre-spend receipt. `--stage` is required.

| Stage | Plan | Mutations (each through `timeout.py`) | Never |
|---|---|---|---|
| `base-apply` | yes | Terraform apply of the verified plan copy (the runtime disabled; this creates the ECR repositories), then the G5 runtime archive upload of a **private copy** (`aws s3 cp` with that copy's own sha256 as metadata, then size and sha256 verified against the copy; `--skip-runtime-archive` skips it) | push, ECS checks |
| `push` | **none** | `ecr-repositories-exist`; `verify-local-images` (each local tag must resolve to the image ID in the release manifest and be `linux/amd64`); registry login; `docker tag <verified image ID> <ecr>/<repo>:<commit>` and `docker push`; `record-digests` (the registry digest from `aws ecr describe-images` must equal the digest `docker push` printed); then the **push record** is written | apply, upload |
| `runtime-apply` | yes | `push-record` (required for this commit, account, region, environment and the four repositories); `ecr-repositories-exist`; `verify-registry-images` (each `<repo>:<revision>` must resolve to the digest recorded by the verified push, **before apply**; with `--reuse-images` it must equal the previous deploy manifest's digest and no push record is needed); Terraform apply of the verified copy; `record-ecs`. With `--source-commit SHA` it is the **infrastructure rollback that keeps the running runtime** (see Rollback behavior) | push, upload |
| `cleanup-prepare` | yes (from `cleanup.sh --prepare`) | Terraform apply of the verified preparation plan, after re-checking the preparation policy | push, upload |

The order of checks before any stage mutates: `terraform-version`, `clean-tree`, `approval-record`, `stage-match`, `commit-match` (source commit equals `APPROVED_COMMIT`), `region-match`, `environment-match`, `prespend-receipt`, then for plan stages `plan-checksum`, `plan-provenance`, `state-binding`, `plan-inspect`, then `release-manifest` (push and runtime-apply), `runtime-archive` (base-apply), `push-record-path` (push) or `push-record` (runtime-apply), and, with `--execute`, `account-check`. With `--reuse-images` or `--image-revision` the step `image-revision-binding` runs right after `prespend-receipt`, and for `base-apply` and the rollback that keeps the runtime `runtime-preservation` runs right after `plan-inspect`.

**Verified plan copy and receipt.** The plan file is copied once into the private run directory, its sha256 must equal `APPROVED_PLAN_SHA256`, and that copy is what `terraform show -json` inspects and Terraform applies; the original path is never applied, and the copy's sha256 is re-verified immediately before apply. The receipt is copied once too and its sha256 must equal `APPROVED_RECEIPT_SHA256`. **Provenance.** `plan_sha256` must equal the verified copy's, `clean` must be true, `commit` must equal the approved source commit, `scripts_commit` must equal HEAD, `purpose` must match the stage, and account hash, region, environment, planned environment and project, terraform version and image revision must match.

**State binding (R1).** The live state file must exist, carry the receipt's `lineage` and still have its `serial` and `sha256` (or still be absent for a `--expect-new-state` plan). It is checked at `state-binding` (also in a dry run: it is a local read) and **again immediately before every apply**. Terraform's own stale-plan check applies on top. The apply runs in the same state-bound materialized root as the plan, so it updates the live state file.

**Independent inspection (R8).** `plan-inspect` is **deferred to `--execute`**: a dry run prints `terraform init -lockfile=readonly` and `terraform show -json <verified copy>` as `DRY-RUN CMD:` lines, says the inspection is deferred, and runs **no** Terraform command beyond the version probe (no aws and no docker either). With `--execute` the inspection is mandatory before the account check and every mutation: the source commit is re-materialized from git (bound to the live state) and its tree hash must equal `source_tree_sha256`; `terraform init` (read-only lock file); then `terraform show -json <verified copy>` must report the approved region as the aws provider region (and in the `aws_region` variable), an `aws_account_id` whose sha256 equals `APPROVED_ACCOUNT_SHA256`, the `environment` and `project` the scripts operate on, and an `image_revision` equal to the deployment revision (`base-apply` expects none; `runtime-apply` expects HEAD, or the previous manifest's revision with `--reuse-images`; `cleanup-prepare` the receipt's).

**Push record (R4).** `--stage push` creates `target/release/<HEAD>/push-record.json` (0600, exclusive; an existing record or a symlink there refuses before any push) only after every digest was verified: `{schema scholarchain.push-record.v1, commit, account_sha256, region, environment, images: [service, repository, tag, pushed_digest, local_image_id]}`. `runtime-apply` requires it (`--push-record FILE` overrides the path): the commit, account, region, environment, the four repositories and tags must match, and every registry digest must equal the recorded pushed digest **before apply**, so a pre-existing tag pointing at other bytes cannot pass.

**ECS verification (runtime-apply).** After apply, `aws ecs describe-services` must return all four services, and for each the **active** task definition (`aws ecs describe-task-definition`) must reference `<ecr host>/scholarchain-course/<service>:<revision>` (or `@<verified digest>`) for **its own** service. A missing service, a stale revision or another service's image fails the stage with exit 4 and no deploy manifest is written, so nothing is recorded as a success. Task-definition ARNs in the manifest are redacted.

**Runtime archive (R9, N5).** The archive is copied **once** into the private run directory; its size and sha256 are verified on the **copy** against the config pins; the same copy is re-hashed immediately before upload (after the long apply), uploaded, and the S3 metadata sha256 is that copy's hash, never a config value; the uploaded object's size and metadata are verified against the copy. Replacing the original during the apply changes nothing that is uploaded or recorded. **S3-computed checksum (N5).** The metadata is what the script set itself, so after the upload `aws s3api head-object --checksum-mode ENABLED` also returns the object's `ChecksumSHA256` (S3 computes it while validating the `--checksum-algorithm SHA256` upload; base64 of the raw sha256) and it must equal the private copy's. The real 322 MB archive is uploaded in parts, so S3 reports a **composite** value `<b64>-<parts>`; it is then verified part by part: `aws s3api get-object-attributes --object-attributes ObjectParts` lists each part's size and checksum, each is compared with the matching byte range of the private copy, and the composite is recomputed from them. A truncated part list, a differing part or a missing checksum fails the stage with exit 4 and nothing is recorded as a success. No chunk size is assumed.

### First deployment (Phase 14), every step separately approved (recorded order)

Base apply, push, runtime plan, new approval, runtime apply. Three approval records, three pre-spend receipts.

1. `scripts/plan.sh --env course --region R --profile P --execute` (runtime disabled: the **base plan**; add `--expect-new-state` only if no local state file exists yet). Read `PLAN-TEXT`, check the `PLAN-ACTION` list, write the pre-spend receipt, write approval record A (`APPROVED_STAGE=base-apply`, with the plan and receipt hashes `plan.sh` printed), then `scripts/deploy.sh --stage base-apply --plan <base plan> --region R --profile P --execute`. This creates the ECR repositories and uploads the G5 archive.
2. `scripts/package.sh` at the same clean commit (images, release manifest).
3. Approval record B (`APPROVED_STAGE=push`: commit, account hash, region, environment, pre-spend hash; **no plan or receipt line**) and a fresh pre-spend receipt, then `scripts/deploy.sh --stage push --region R --profile P --execute`. Images are pushed by commit SHA, registry digests verified, the push record written. It refuses (`ecr-repositories-exist`, nothing pushed) while the repositories are missing.
4. `scripts/plan.sh --env course --region R --profile P --image-revision <HEAD SHA> --execute` with the runtime variables enabled in the private variable file (the **runtime plan**, made after the push against the state the base apply left).
5. Approval record C (`APPROVED_STAGE=runtime-apply`, the runtime plan and receipt hashes) and a fresh pre-spend receipt, then `scripts/deploy.sh --stage runtime-apply --plan <runtime plan> ... --execute` (push record and registry digests verified, apply, four ECS services verified).

`runtime-apply` refuses (`push-record`) without step 3, and `push` and `runtime-apply` refuse (`ecr-repositories-exist`) until step 1 has created the repositories. Do not commit any approval record before deploying.

Between step 1 and step 5 the state holds the ECS cluster and the ECR repositories but no ECS service or load balancer, so the runtime is **not live** (T1): an infrastructure rollback in that window is the runtime-disabled kind (no `--deployed-*`), and a rollback bound to the push record of step 3 is refused because it would create the runtime.

## Rollback behavior (policy 13-5)

No console or CLI mutation outside Terraform, and no data repair. Each rollback needs a NEW approval record (with `APPROVED_RECEIPT_SHA256` and `APPROVED_ENVIRONMENT`), a fresh pre-spend receipt and a plan receipt, exactly like a deployment.

- **Application rollback** (`rollback.sh --env E --region R --previous-manifest <deploy-manifest.json>`): verifies the previous manifest holds sha256 digests for all four services; verifies each registry tag still resolves to the recorded digest (`aws ecr describe-images --image-ids imageTag=<previous commit>`; printed in dry run, compared in `--execute`); then
  1. `--stage plan`: re-plans through `plan.sh --image-revision <previous commit SHA>` (the plan lands in a fresh `PLAN_DIR/<run-id>/`; the path is printed as `PLAN-FILE`);
  2. the human reviews it and writes a new approval record (`APPROVED_STAGE=runtime-apply`) and pre-spend receipt;
  3. `--stage deploy --plan <PLAN-FILE> [--approval F --prespend F]`: `deploy.sh --stage runtime-apply --reuse-images <previous manifest>` applies the verified plan copy, pushes nothing, and verifies the four ECS task definitions for the previous revision.
- **Infrastructure rollback** (`--mode infra --previous-commit SHA`): the **current** scripts run against the Terraform source as committed at `SHA`; the previous tree does **not** need to contain `scripts/` and nothing is checked out (the script never changes the work tree). Which of two kinds it is depends on what the **live state** shows. `rollback.sh` reads the state file locally (step `runtime-state`: only each resource's module path, type and instance count, never an attribute).

  **What "runtime live" means (T1, repair round 4).** The runtime is live when it is **deployed**, and that is decided only from the pinned `RUNTIME_LIVE_INDICATOR_TYPES` of `RUNTIME_LIVE_MODULE` (`module.runtime`): the resources that `modules/runtime/compute.tf` creates only when `enabled && image_revision != null`, with the instance count of a complete runtime: `aws_ecs_service=4` (`for_each = local.active_services`), `aws_lb=1` and `aws_lb_target_group=1` (`count`), `aws_lb_listener=0-1` (`count`, which also needs `certificate_arn`). The ECS cluster (`aws_ecs_cluster.course`), the service-discovery namespace and the four ECR repositories have **no count** (and `module "runtime"` in `main.tf` has none), so the first runtime-disabled `base-apply` already leaves them in the state: they are **not** indicators, and a state after the base apply is "runtime not live". The other gated dependents (task definitions, service-discovery services, autoscaling targets and policies) are not indicators either. `test_runtime_base_apply.SourceDerivedClassificationTests` re-derives this classification from the Terraform source. The verdict is one of three:

  | Live state | Verdict | `rollback.sh --mode infra` | `deploy.sh` `runtime-preservation` |
  |---|---|---|---|
  | no instance of any indicator type (empty state, or after the base apply: cluster, namespace, ECR repositories, network, data, KMS, log groups) | `RUNTIME-LIVE: no` | runtime-disabled rollback accepted; `--deployed-*` **refused** ("would CREATE the runtime") | base-apply passes (nothing to preserve); a carried `runtime-apply` is refused ("would CREATE the runtime") |
  | every indicator count complete (four services, load balancer, target group, 0 or 1 listener) | `RUNTIME-LIVE: yes` | `--deployed-*` required; without it **refused** | no delete or replace of a protected type |
  | anything in between (for example a load balancer without services, only some services, a target group without its load balancer) | `RUNTIME-LIVE: partial` | **refused** at `runtime-state`, with or without a binding, before any registry, plan or apply call | **refused** (fail closed) for base-apply and the carried apply |

  A partial runtime (for example after an interrupted runtime apply) is ambiguous: neither rollback kind can be shown to keep or to leave it as it is, so the human decides the recovery. The safety-net types are the separate pinned `RUNTIME_LIVE_PROTECTED_TYPES`: every indicator type **plus the ECS cluster**, which stays protected against delete or replace while the runtime runs on it (with no deployed runtime there is nothing on the cluster to preserve). `verify.py` refuses a configuration in which an indicator type is not protected.

  - **Runtime not live (runtime disabled; also the state right after the first base apply).**
    1. `--stage plan`: `plan.sh --source-commit SHA` extracts `infra/terraform` of `SHA` with `git archive` into `PLAN_DIR/<run-id>/source/SHA` (only committed bytes), makes it read-only and **binds it to the live local state file** (`TERRAFORM_STATE_FILE`) with a generated `backend "local"` override, so the plan is made against the **existing** state of the live stack and never proposes to create a resource it already manages (proven with real Terraform on a populated local state and an older commit without `scripts/`: `test_terraform_state_binding.py`). The receipt records `commit=SHA`, `scripts_commit=HEAD` and the state's lineage, serial and sha256;
    2. new approval record with `APPROVED_COMMIT=SHA` and `APPROVED_STAGE=base-apply`, plus a pre-spend receipt;
    3. `--stage deploy --plan <PLAN-FILE>`: `deploy.sh --stage base-apply --source-commit SHA --skip-runtime-archive` verifies the same chain, **refuses when the state file is missing, has another lineage or changed after the plan**, and applies the verified copy from the same state-bound materialized source, which updates the live state file.
  - **Runtime live (S1: the rollback keeps the running runtime).** A plan without an image revision creates no ECS service, load balancer or listener (`modules/runtime/compute.tf` counts them on `image_revision`) and the runtime precondition in `phase12b.tf` fails when the runtime is enabled without one, so a rollback that carried no revision would delete the runtime. The rollback therefore **carries the currently deployed image revision**, bound to exactly one of:
    - `--deployed-manifest FILE`: the `deploy-manifest-runtime-apply-*.json` written by the runtime-apply that put the revision live. It must be a **runtime-apply** manifest (a push or base-apply manifest proves nothing is running), for the approved region, the four `scholarchain-course/<service>` repositories (this is also how the environment is bound), all four ECS services recorded, and (checked by `deploy.sh`, which has the approved account) the approved account hash;
    - `--deployed-push-record FILE`: the push record of that revision (`target/release/<revision>/push-record.json`); the revision is the record's own commit, and the record must name this account, region, environment and the four repositories.

    Steps: (1) `rollback.sh --mode infra --previous-commit SHA --deployed-manifest|--deployed-push-record FILE --stage plan`: `runtime-state` (a live runtime without a binding is **refused**, and so is a binding while the state shows no deployed runtime, also right after the base apply when only the cluster and the ECR repositories exist: that rollback would create it; a partial runtime is refused too), `deployed-revision`, then **`verify-registry-digests`**: `aws ecr describe-images` for `<repo>:<revision>` of all four repositories must equal the manifest's or the record's digests, before any plan; then `plan.sh --source-commit SHA --image-revision <revision>`, and at once the **`runtime-preservation`** check of the plan receipt's action list: while the state shows the runtime, a plan that **deletes or replaces** any resource of `module.runtime` of a protected type (`RUNTIME_LIVE_PROTECTED_TYPES`: ECS cluster, service, load balancer, listener, target group) is **refused fail-closed** (`RUNTIME-PRESERVATION-FAILED: ...`, exit 3, "do NOT approve or apply it"). Task definitions are not protected types: a new revision legitimately replaces them. (2) The human writes a **new** approval record: `APPROVED_STAGE=runtime-apply`, `APPROVED_COMMIT=SHA` (the Terraform source, not HEAD), the plan and receipt hashes, account hash, region, environment and a fresh pre-spend receipt. (3) `--stage deploy --plan <PLAN-FILE> [--approval F --prespend F]`: `deploy.sh --stage runtime-apply --source-commit SHA (--reuse-images <manifest> | --image-revision <revision> --push-record <record>)`.

    **Stage binding.** No new stage was added: the carried plan is a `runtime-apply` (the only stage whose plan has an `image_revision`), and the approval record stays unambiguous because `deploy.sh` compares `APPROVED_STAGE` with `--stage`, `APPROVED_COMMIT` with the **source** commit (SHA, not HEAD), and the receipt (hash named by `APPROVED_RECEIPT_SHA256`) records `commit`=SHA, `scripts_commit`=HEAD and `image_revision`. A record for a plain runtime-apply (commit = HEAD) is refused (`commit-match`) when `--source-commit SHA` is given, a `base-apply` record is refused (`stage-match`), and the carried record is refused for a plain runtime-apply. `--source-commit` with `runtime-apply` without `--reuse-images` or `--image-revision` is refused.

    `deploy.sh` re-verifies everything before apply: the bound manifest or push record (`image-revision-binding` / `push-record`: stage, account, region, repositories, the four ECS services), **the registry digests again** (`verify-registry-images`; a moved tag refuses before apply), the pre-spend receipt, the approval, the receipt and the plan target (the plan's `image_revision` must equal the bound revision: receipt, and the saved plan's own variables with `terraform show -json`), the state binding, and **`runtime-preservation`** twice (the receipt's actions, also in a dry run, and with `--execute` the verified plan's own `show -json`). The same `runtime-preservation` check also guards every `base-apply` (a runtime-disabled plan applied while the state shows the deployed runtime would delete it; on a post-base-apply state a base-apply that keeps the cluster, by a no-op or an update, passes; a partial runtime refuses). After the apply, **all four ECS services** and their active task definitions must reference the bound revision (or its verified digest) before the deploy manifest is written; a stale, swapped or missing service exits 4 and nothing is recorded as a success. A dry run still runs only the Terraform version probe.

    Limits: an application rollback (`--previous-manifest`) keeps its existing manifest check (digests and revision only); the stricter binding above is for the infrastructure rollback. A plain `runtime-apply` at HEAD is not covered by `runtime-preservation`.

  Each `deploy.sh` run removes its own run directory at exit; a plan's run directory stays until you remove it (`chmod -R u+w target/plans/<run-id>` first: the source trees are read-only). The `terraform init` for a source needs its providers (network init, or `TF_PLUGIN_CACHE_DIR`).

## Cleanup behavior and preservation policy (F3, R5)

`cleanup.sh --env E --region R` prints the read-only inventory commands (`terraform state list` for every root, a tag-based `aws resourcegroupstaggingapi get-resources`), the pinned preservation rules, the protection check and the commands `--execute` would run; it runs no Terraform command beyond the version probe and writes nothing. Only the main root is destroyed; account-level roots and spikes are inventoried and preserved. The destroy root runs from a read-only `git archive` of HEAD bound to the live state (like `plan.sh`).

**Policy (user decision for repair round 1, pinned in `scripts/config/release.conf`).** Never removed: Terraform state/backend (`module.foundation.`: state bucket, lock table, budget); all S3 buckets and objects and their bucket-level configuration (type prefix `aws_s3_bucket`, `aws_s3_object`; `module.datalake.`); S3 Vectors (`aws_s3vectors_`, `module.s3vectors.`); the KMS keys, aliases and key policies that keep that data readable (`aws_kms_`); CloudWatch log groups needed for grading (`aws_cloudwatch_log_group`). Teardown: ECS/ECR runtime (`module.runtime.`), EMR, Neptune, DynamoDB (`module.dynamodb.`), SQS (`module.messaging.`), Step Functions (`module.workflow.`) and the network (`module.network.`: NAT/EIP, endpoints, VPC and children), plus the runtime IAM roles/policies/instance profile and the alarms/dashboard that a targeted run pulls in as dependents (`module.identity.aws_iam_role.task|execution|emr_ec2|emr_service|neptune_loader`, `aws_iam_role_policy.`, `aws_iam_instance_profile.emr`, `module.observability.aws_cloudwatch_metric_alarm.|aws_cloudwatch_dashboard.`). The deployment role and everything else are UNLISTED (A2, the teardown set, is unchanged and still awaits the human decision). PRESERVE wins over TEARDOWN; the match uses the address with any `[index]` removed.

**Deletion protection and the preparation step (R5).** Terraform protects Neptune (`deletion_protection`), the query load balancer (`enable_deletion_protection`), the DynamoDB tables (`deletion_protection_enabled`) and the ECR repositories (`force_delete=false`) while `cleanup_mode=false`; a delete-only plan cannot remove them. Before the destroy listing and before a confirmed run, `cleanup.sh` reads the current state (`terraform show -json` into a private temp file; no value printed) and **refuses the whole destructive sequence** (`RESULT: REFUSED step=protection-check`, `PROTECTION-ACTIVE: <address> <flag>` lines, `PREPARE-REQUIRED`) while any **teardown** resource still has such a flag active (`CLEANUP_PROTECTION_RULES`; protected preserved resources such as the state lock table are not blockers). The separately reviewed preparation:

1. `cleanup.sh --env E --region R --prepare [--image-revision <deployed revision>] --execute`: a normal plan (not destroy) with `-var=cleanup_mode=true` and `-target` for exactly the protected teardown resources, saved with a receipt (`purpose cleanup-prepare`). It is **refused** (`step=prepare-policy`, `POLICY-VIOLATION:` lines, no receipt) unless every change is an in-place **update** of a teardown resource and changes only the protection and force flags of `CLEANUP_PREPARE_ALLOWED_ATTRS` (Neptune `deletion_protection`, `skip_final_snapshot`, `final_snapshot_identifier`; ALB `enable_deletion_protection`; DynamoDB `deletion_protection_enabled`; ECR `force_delete`): any create, delete, replace, preserved or unlisted resource, other attribute or newly unknown attribute refuses. With no protection active it reports that nothing is needed. Nothing is applied. It prints `PLAN-FILE`, `PLAN-RECEIPT` and the candidate approval lines with `APPROVED_STAGE=cleanup-prepare`.
2. The human writes a **new** approval record and a pre-spend receipt; `scripts/deploy.sh --stage cleanup-prepare --plan <PLAN-FILE> ... --execute` applies exactly that plan through the same approval path (plan, receipt and state checks, pre-spend re-verification, policy re-check on the verified copy).
3. The listing below now passes the protection check and proceeds to the token. `cleanup_mode` also switches S3 and S3 Vectors `force_destroy`, but those preserved resources are never targeted and the S3 `prevent_destroy` guards stay. No IAM is widened.

**`--execute` runs twice.**

1. **Listing** (no `--confirm`): live STS account hash; the fresh run directory and materialized source; inventories (`before-inventory.txt`); the destroy root's `state list` is classified (`TEARDOWN-TARGET:` lines for the base addresses to target); the **protection check**; `terraform plan -destroy -var=cleanup_mode=true -target=<each teardown address> -out=<run dir>/destroy-<env>.tfplan`; `terraform show -json` and `show -no-color` of that saved plan (private files); the policy check; every action printed as `DESTROY-ACTION: <delete|replace> <address>` (complete, sorted), `DESTROY-PLAN-SHA256`, `DESTROY-PLAN-FILE`, `CONFIRM-BINDING`, `CONFIRM-TOKEN`; then `RESULT: REFUSED` (exit 3): nothing is destroyed. The plan is REFUSED (step `destroy-policy`, `POLICY-VIOLATION:` lines, no token offered) when any delete or replace touches a preserved class, when any delete is not in the teardown set, or when it holds a non-delete action.
2. **Confirmed** (`--confirm TOKEN --plan <DESTROY-PLAN-FILE>`): does **not** re-plan. The saved plan is copied once into the private run directory and hashed, re-inspected with `terraform show -json`, re-checked against the policy, and the token is recomputed from that copy plus the **live** STS account hash; any difference (plan bytes, action list, account, region, environment) refuses; the protection check runs again. Only then is the verified copy applied (its sha256 re-verified immediately before apply), followed by `after-inventory.txt`.

**Token** = lowercase hex sha256 of the UTF-8 text
`scholarchain-destroy-token-v1\nplan_sha256=<hex>\naccount_sha256=<hex>\nregion=<region>\nenvironment=<env>\n` followed by each sorted action line (`delete <address>`) and a newline.

It needs **two passes**: the first is expected to fail at `aws_eip.nat` `DisassociateAddress` 403 (carried item 24); run the listing again (fresh plan, new token) for pass 2 and do not widen IAM. S3 buckets keep `prevent_destroy`. **Outputs (R2):** each run has a fresh evidence directory `target/cleanup-evidence/<run-id>` (or `--evidence-dir`, which must lie inside `CLEANUP_EVIDENCE_DIR` and may not alias or nest in `PLAN_DIR`); every evidence and plan output must be absent beforehand, confined, symlink-free and distinct, and is created exclusively. Evidence (D20): `before-inventory.txt`, `after-inventory.txt`, `destroy-plan.sha256`, `destroy-actions.txt`; the saved plan, JSON and text stay private in the run directory.

### Smoke test

`smoke-test.sh` reads the API key from the environment variable **named** by `--api-key-env` (default `SCHOLARCHAIN_SMOKE_API_KEY`; the target URL may come from `SCHOLARCHAIN_SMOKE_URL`). The value is registered for redaction and is never printed, logged or written. Plain `http://` is accepted only for a loopback host, so a bearer key never travels in clear text to a remote host; a URL with user-info, a path, a query or a fragment is refused (exit 3). The contract it follows is `modules/services/README.md`: `GET /healthz` and `/readyz` need no key; `POST /v1/query` carries `Authorization: Bearer <key>` and an `Idempotency-Key`, and a `200` answer is used directly while a `202` job reference is followed (`GET /v1/jobs/{id}` until `SUCCEEDED`, then `/result`); the first evidence id cited by a claim is fetched with `GET /v1/evidence/{id}`; the repeat with the same key must return the same `queryId` (and job id) and leave `GET /v1/queries/{id}/evidence` unchanged; a request with no key and one with an invalid key must both be `401 UNAUTHORIZED` and the bodies must not echo the key. The default body is the one supported offline-synthetic fixture question (`Synthetic fixture: publication count for A`); `--query-body FILE` supplies another for a deployed endpoint. Timeouts: `TIMEOUT_SMOKE_REQUEST_SECONDS` per request and `TIMEOUT_SMOKE_JOB_SECONDS` for a job (flags `--request-timeout`, `--job-timeout`).

### Bounded pipeline (`run-bounded-pipeline.sh`)

Prerequisites: the cluster exists (Terraform, Subphase 13C), the packaged Phase 6 job and the portable runtime are installed on the nodes by the bootstrap at `PIPELINE_RUNTIME_DIR` / `PIPELINE_JOB_JAR_PATH`, EFS is mounted at `PIPELINE_EFS_MOUNT` on every node, the bootstrap wrote the Java 17 home it resolved to `PIPELINE_JAVA_HOME_FILE`, and the five artifacts (Hadoop submit JAR and dependency bundle, entity-resolution JAR, policy and config, Spark config template) are cluster-visible. **The entity-resolution JAR has no packaging task yet** (`packageRelease` builds only the Hadoop, Spark job and service artifacts): until the build owner adds one, the ER step can be planned and dry-run but not run (`--er-jar` is a reference the human supplies).

Environment variable **names**: `SCHOLARCHAIN_EMR_CLUSTER_ID`, `SCHOLARCHAIN_AWS_REGION`, `AWS_PROFILE` (the human's approved profile, never a default), `SCHOLARCHAIN_REPO_ROOT`. Test-only: `SCHOLARCHAIN_CONFIG_FILE`, `SCHOLARCHAIN_PRICING_FILE`, `SCHOLARCHAIN_TEST_CLOCK_FILE`, `SCHOLARCHAIN_TEST_DEADLINE_SECONDS` (each honoured only together with the announced `SCHOLARCHAIN_CONFIG_FILE`; `SCHOLARCHAIN_TEST_DEADLINE_SECONDS` can only shorten the wall-clock cap). No pinned value (caps, ceilings, rates, Spark properties) can be set from the environment.

**Steps** (one EMR step each via `command-runner.jar`, submitted in order; each step is a short `bash -c` launcher plus `KEY=VALUE` parameters, see **Finding C1** below; the run stops at the first step that is not `COMPLETED`). All run state lives on EFS under `<mount>/runs/<run-id>/`; a run directory is never reused.

| # | Step | What the body does |
|---|---|---|
| 1 | `stage-in` | refuses unless the mount is a real mount point and the run directory is new; checks the input size against `PIPELINE_MAX_INPUT_BYTES`; `aws s3 cp --recursive` of the input prefix to EFS (G1 option ii) |
| 2 | `hadoop-prep` | localizes the Hadoop submit JAR, the dependency bundle and the prep config and verifies each sha256; repeats the Phase 4 ceiling check on the cluster; `hadoop jar ... HadoopPrepMain -Dmapreduce.job.tags=<run-id> -libjars ... --once --execution-mode cluster --run-id <run-id>` over `file://` inputs on EFS with the dataset snapshots from the datasets manifest |
| 3 | `entity-resolution` | finds the one completed Hadoop run (`_SCHOLARCHAIN_COMPLETE`); reads the Java home the bootstrap resolved (never hard-coded; must be Java 17); runs `Phase5Main resolve --llm-mode disabled` as a single JVM on the primary node |
| 4 | `spark-class-origin` | `spark-submit` of `Phase12Readiness probe ... distributed` on YARN, then a verifier that **fails closed**: driver and executor must both report Java 17, the pinned Spark and Scala library versions, Spark/`scala-library`/`scala-reflect` loaded from the runtime jar directory, `scala3-library` loaded from the packaged job JAR with the approved sha256, and identical class and jar hashes on both sides |
| 5 | `spark-job` | re-checks the job JAR sha256 and the class-origin result (refuses to start without a passing one), renders the Phase 6 config (only `hadoopRunRoot`, `entityResolutionRunRoot`, `outputRoot` and `checkpointDirectory` are set), then `spark-submit --master yarn --deploy-mode cluster` with every property of `scripts/config/spark-12-10.conf` (decision 12-10: `spark.yarn.jars=local:/opt/scholarchain-runtime/jars/*`, `populateHadoopClasspath=false`, codecs without LZO, `spark.authenticate`, AES-CTR with `authEngineVersion=1`, IO encryption, G2 `dynamicAllocation.shuffleTracking.enabled=true`), `spark.yarn.tags=<run-id>`, the resolved Java 17 as the AM and executor `JAVA_HOME` and `spark.dynamicAllocation.maxExecutors=(core + task) x PIPELINE_MAX_EXECUTORS_PER_NODE` |
| 6 | `copy-out` | checks the result size against `PIPELINE_MAX_COPYOUT_BYTES`, writes a sha256 manifest and copies `hadoop`, `er`, `spark` (with the event logs under `.event-logs`), `results` and `config` to `<output-prefix>/<run-id>/` |

**Item 1 (carried 12D finding).** `timeout` kills only the `spark-submit` or `hadoop` client, not the YARN application. Every YARN-submitting body tags the application with the run id (`spark.yarn.tags`, `mapreduce.job.tags`) and runs `yarn application -list -appStates NEW,NEW_SAVING,SUBMITTED,ACCEPTED,RUNNING -appTags <run-id>` then `yarn application -kill <id>` for each match when the step's `timeout` fires (exit 124, 137 or 143) and again from the shell's `EXIT` and `TERM` traps. The step timeouts are `PIPELINE_STEP_WEIGHTS` percent of `--max-runtime-minutes` (sum at most 100), so they can never exceed the run's hard cap. **13C finding B1:** the WHOLE step body (stage-in, copy-out and every `localize` copy included) now runs on the node under `timeout --kill-after=PIPELINE_KILL_AFTER_SECONDS <its timeout_seconds>`: the installed step runner (`scripts/emr/sc-step.sh`, wrapper mode) runs `timeout ... bash sc-step.sh __body <step> ...` in the background, forwards TERM and INT to it (an EMR cancel) and prints `STEP-FAIL <step>: exceeded the <n>s step timeout` on exit 124 or 137. The timed command runs as its own process group (`set -m`): on a nonzero exit, a timeout or a cancel the wrapper sends TERM to the whole group, waits up to `PIPELINE_KILL_AFTER_SECONDS`, and KILLs whatever is left (`STEP-WARN <step>: processes of the step process group <id> were still running after the step; killed with SIGKILL`), so a grandchild that ignores SIGTERM (a stuck copy) cannot outlive the step even though `timeout` itself signals only its own group. A hung `aws s3 cp` or `hadoop fs -copyToLocal` is killed at the step timeout instead of keeping the cluster busy forever (the idle-based auto-termination never fires on a busy cluster). The `STEP-TIMEOUT` line says exactly that; `--execute` also asks EMR to cancel the running step (`SEND_INTERRUPT`) when the wall-clock cap passes. The cluster's auto-termination stays set: `--execute` runs `aws emr describe-cluster`, `aws emr get-auto-termination-policy` and `aws emr list-instance-groups` before anything paid and refuses (exit 4) a cluster that is not `WAITING` or `RUNNING`, has no auto-termination idle timeout (60 to `--max-idle-seconds` or `PIPELINE_MAX_IDLE_TIMEOUT_SECONDS`), or holds another instance type or more nodes than approved; the dry run prints the three commands.

**Finding C1 (13C repair round 1): step form and the EMR argument limit.** EMR accepts at most **10,280 characters per string** in a step's `HadoopJarStepConfig.Args`. The 13C wrapper embedded the whole step body in ONE `bash -c` argument (about 11.8 KB for `spark-job`, 10.2 KB for `spark-class-origin`, longer with real bucket and prefix names), so the step could not have been submitted. Each EMR step is now

```
bash -c '<static launcher, about 330 characters>' sc-step <sha256 of sc-step.sh> <STEP> KEY=VALUE KEY=VALUE ...
```

* **Installed files, one directory.** The static program text lives in four files under `scripts/emr/`: `sc-step.sh` (the B1 wrapper plus the six step bodies), `sc-ceiling-check.py`, `sc-class-origin-verify.py` and `sc-render-spark-config.py`. The bootstrap installs each as a sha256-verified `--artifact` into `PIPELINE_STEP_BIN_DIR` (pinned in `release.conf`, `/opt/scholarchain-spike/bin`; the bootstrap's `STEP_BIN` and `infra/terraform/emr-step-programs.json` `bin_dir` equal it, and tests compare all three). The Python programs are the SAME files the plan builder and the tests run locally (the ceiling check at plan time, `pipeline.py verify-class-origin`), so what is tested is what runs.
* **On-node verification, fail closed.** The launcher checks `sc-step.sh` on the node against the sha256 the pipeline computed from the repository file and refuses (`STEP-FAIL sc-step: sha256 mismatch ...`, exit 1, nothing runs) on any difference; `sc-step.sh` checks each Python program against its own `*_PY_SHA` parameter before running it (`STEP-FAIL <step>: sha256 mismatch for the installed step program ...`). Those hashes are part of the approved run configuration (`step_bin_dir`, `step_programs_sha256`), so the human's `APPROVED_RUN_CONFIG_SHA256` also pins the installed programs. A file edited after the plan was approved therefore fails on the node, and a stale Terraform hash fails earlier (below).
* **Parameters, not code.** Every run-specific value (run id, tag, mount, S3 prefixes, artifact references and hashes, ceilings, dataset snapshots, the 22 Spark settings as repeated `SPARK_CONF=key=value`, `MAX_EXECUTORS`, expected versions) is a separate `KEY=VALUE` argument from a per-step allow-list in `sc-step.sh`; a key that is not on the list, a duplicate or a missing key is `STEP-FAIL`. Values are never evaluated, only expanded inside double quotes. The largest argument is the longest artifact reference (at most about 1.1 KB with a 1024-byte S3 key), so every step stays far below the limit.
* **Nothing weakened.** B1 (the whole body under `timeout --kill-after`, own process group, TERM then KILL to the group, `STEP-WARN`), item 1 (YARN kill by run tag on timeout and on EXIT/TERM/INT), the class-origin fail-closed checks and every decision 12-10 setting are the same code moved into `sc-step.sh`; every existing behavioural test runs against the installed files.
* **Refusal before spend.** The plan builder (`pipeline.py plan`, the same code path in the dry run and with `--execute`) refuses any step argument over `PIPELINE_STEP_ARG_MAX_CHARS` (pinned, `10280`, clamped to the EMR limit: it may be lowered, never raised) with exit 3, the marker `STEP: arg-limit` and `STEP-ARG-TOO-LONG: step <name> argument <i> (<KEY>) has <n> characters, over the limit of ...`. This runs at step `plan`, before `g6-gate`, the ledger reservation and the consumption of the single-use approval. Every run (dry or live) prints `STEP-ARG-LENGTHS: <step> limit=<L> count=<n> max=<m> total=<t> lengths=<a,b,...>` for each step.
* **Terraform pin.** `infra/terraform/emr-step-programs.json` holds the sha256 of the four files and the node directory. `pipeline.py plan` refuses with `STEP-PROGRAM-DRIFT` when the manifest differs from the files; `python3 -I scripts/lib/pipeline.py step-manifest --write` regenerates it (`--check` verifies). The root guard `terraform_data.phase12b_guard` requires `emr_config.extra_artifacts` to install each program once at `<bin_dir>/<name>` with exactly that sha256, so a stale or missing hash fails at plan time, not on the node.
* **Printed text.** The dry run's `STEP-BODY-BEGIN/END` block now holds the step as a readable shell command (the launcher and one parameter per line); `bash -c "<that text>"` runs exactly what EMR would, which is how the offline tests exercise it.

**Ceilings and refusals** (before any cloud call, exit 3): the seven Phase 4 `HadoopPrepMain` ceilings (a test compares them with `phase4-emr-smoke.sh`), `PIPELINE_MAX_CAPACITY` (4 instances), `PIPELINE_MAX_RUNTIME_MINUTES` (180; the accepted range is exactly 10 to 180 minutes: each step gets its `PIPELINE_STEP_WEIGHTS` percent of the cap but at least `PIPELINE_MIN_STEP_SECONDS` = 30 s, which the smallest 5 percent share of a 10-minute run equals, so 10 is a real minimum and 9 is refused at step `plan`), the input and copy-out byte ceilings (256 MiB each), a missing sha256 for any artifact (`--artifact-sha256 NAME=HEX`; a local regular file is hashed instead), a malformed datasets manifest, or a Spark property file that departs from decision 12-10.

**Run configuration and manifest.** The dry run prints `RUN-CONFIG-SHA256`: the sha256 of the canonical JSON of everything that decides what the run does and costs (cluster, region, instance type and counts, runtime, budget, estimate and rates, prefixes, artifact hashes, Spark property file hash, dataset snapshots, ceilings, step timeouts; not the run id, a clock or the commit). The human approves that hash. `--execute` writes, exclusively and git-ignored, `PIPELINE_RUNS_DIR/<run-id>/run-manifest.json` (commit, run id and YARN tag, account hash, cluster id, run configuration hash, approval and pre-spend receipt hashes, dataset snapshots, artifact and runtime-archive hashes, limits, teardown, output locations, step timeouts) and `run-result.json` (per-step outcome).

**G6 cost guard.** `estimate = instances x (EC2 on-demand + EMR uplift) x (maximum runtime + auto-termination idle timeout) hours`, rounded up to the cent (**13C finding B3:** the idle tail is billed too; `PIPELINE_MAX_IDLE_TIMEOUT_SECONDS` is now 900 and `--max-idle-seconds` can only lower it; four `m5.xlarge` for 180 minutes now estimate 4 x 0.24 x 3.25 h = 3.12 USD and are refused, where the 13B formula said 2.88 and a 3600 s idle tail would have cost 3.84), printed in the dry run (`ESTIMATE-USD`) and again before `--execute` (it excludes EBS, EFS, S3, NAT and data transfer, as decided). Pinned caps: `EMR_MAX_RUN_USD=3` per run, `EMR_MAX_LIVE_RUNS=3`, `EMR_CUMULATIVE_CAP_USD=9.50` (USD 9.50 of the EMR reserve allocated to Phase 15; about USD 5 stays held back for the pending KMS key charges). `--execute` is **refused** (exit 3, before any cloud call) when the estimate exceeds the per-run cap or the declared `--budget-usd` (also refused in a dry run: such a run could never be executed), when the run ledger `EMR_LEDGER_PATH` (`~/.scholarchain/emr-ledger/runs.jsonl`, see "Run ledger" below) already holds three runs, when the ledger does not exist, when the approval record already started a run, when recorded estimates plus this one exceed 9.50, when the ledger is unreadable (never read as empty), when a reviewed rate is missing (never read as zero), or while `EMR_PRICING_CONFIRMED_BY_HUMAN` is not `true`. A reservation counts for good (a failed run may have spent money); only a human editing the ledger releases one, for example after the Billing page settles. The dry run reports these as `G6-STATUS: --execute would be refused` without failing.

**Run ledger (13C findings B2 and B4).** `EMR_LEDGER_PATH` is `~/.scholarchain/emr-ledger/runs.jsonl`, expanded against `HOME`: it lives **outside the repository and outside sbt's `target/`**, so `sbt clean`, `git clean` and a fresh clone cannot erase the spend record (the 13B location, `target/emr-ledger/`, could, which silently reset the three-run and USD 9.50 caps). The ledger is one JSON line per record: line 1 is `{"event": "init", "initialized_by", "initialized_utc"}`, every later line is a reservation with the run id, estimate, run configuration sha256, **approval record sha256** and time. An **absent ledger refuses `--execute`** (exit 3, before any aws call; a dry run reports it in `G6-STATUS`); an empty file or one whose first line is not the init record is also refused. The human creates it once:

```
scripts/run-bounded-pipeline.sh --init-ledger     # records who (id -un) and when; takes no other argument; makes no cloud call
```

`--init-ledger` **refuses when the ledger already exists** and never overwrites it. **Reset risk (read this):** deleting or replacing `runs.jsonl` by hand reopens the three-run and USD 9.50 caps and also makes every earlier approval record usable again; do it only deliberately (for example after the Billing page settles), and note it in the phase evidence. The ledger is private (0600 in a 0700 directory), created exclusively, never reached through a symlink, written under a file lock, and refused if it would sit inside the repository. **Approvals are single-use (B4):** a reservation stores the sha256 of the approval record, and any later run with the same record is refused before any aws call, even after a failed run; to run again the human writes a new record (any change to the file, for example a `Approval serial: 2` line, which the parser ignores, changes its sha256). Tests use a temporary `HOME`.

**Pricing and the human confirmation.** `scripts/config/emr-pricing.conf` holds one EC2 and one EMR hourly rate per instance type the Terraform variable allows (`m5.xlarge`, `m5.2xlarge`), the region, the retrieval date and the source URLs. The rates were read on 2026-11-06 from AWS's public Price List bulk files for us-east-2 (EC2 `.../AmazonEC2/current/us-east-2/index.csv`, Linux, shared tenancy, on-demand; EMR `.../ElasticMapReduce/current/us-east-2/index.json`), anonymously and read-only: `m5.xlarge` 0.192 + 0.048 and `m5.2xlarge` 0.384 + 0.096 USD per hour. **`EMR_PRICING_CONFIRMED_BY_HUMAN=false` is committed and `--execute` refuses until the human has checked the sources and changes it to `true` in that file** (an environment variable cannot do it; a rate or pricing variable in the environment is ignored and announced).

**Approval record for `--execute`** (`--approval FILE`, default `RUN_APPROVAL_RECORD_PATH`; written by the human, never by an agent). Each line exactly once as `KEY=value`, no quotes, no spaces around `=`, no indent or CR; other text is ignored. Any missing, duplicate or malformed line, any value that differs from the run, and any extra key refuses with exit 3 and a `STEP:` marker (`approval-record`, `approval-match`).

| Line | Must equal |
|---|---|
| `APPROVED_ACTION=run-bounded-pipeline` (or `run-experiment`) | the action being run |
| `APPROVED_COMMIT=<40 hex>` | `git rev-parse HEAD` of a **clean** tree (only the literal `RUN_APPROVAL_RECORD_PATH` is exempt from the dirty-tree refusal) |
| `APPROVED_ACCOUNT_SHA256=<64 hex>` | sha256 of the 12-digit account id string with no newline (`printf '%s' "$id" \| shasum -a 256`), compared with `aws sts get-caller-identity` before the cluster is described; the raw id is never printed |
| `APPROVED_REGION=<region>` | `--region` |
| `APPROVED_CLUSTER_ID=<j-...>` | `--cluster-id` |
| `APPROVED_RUN_CONFIG_SHA256=<64 hex>` | the dry run's `RUN-CONFIG-SHA256` |
| `APPROVED_BUDGET_USD=<decimal>` | `--budget-usd` (numerically) |
| `APPROVED_MAX_CAPACITY=<integer>` | 1 primary + core + max task nodes |
| `APPROVED_MAX_RUNTIME_MINUTES=<integer>` | `--max-runtime-minutes` |
| `APPROVED_TEARDOWN=auto-termination` | the literal (the cluster must have an idle timeout) |
| `APPROVED_PRESPEND_SHA256=<64 hex>` | sha256 of the pre-spend receipt file |
| `APPROVED_MANIFEST_SHA256=<64 hex>` | **`run-experiment` only**: sha256 of the committed manifest; refused for `run-bounded-pipeline` |

The pre-spend receipt is the 13A file (schema, 24 h age, USD 20 headroom, `--prespend FILE`, default `target/phase14/prespend-receipt.json`). It is verified from a private copy before anything else and **re-verified immediately before each of the six step submissions** (`pre-spend receipt rejected before step-<name>`: that step and every later one is not submitted). The dry run prints every `APPROVAL-LINE:` for the human to paste. A reviewed dry run is not approval to execute.

### Experiment runner (`run-experiment.sh`)

It runs **only** a manifest that is tracked by git and unchanged against HEAD (an untracked, git-ignored, modified, staged-but-different or out-of-repository file is refused with `step=manifest-committed`; the bytes must equal `HEAD:<path>`), and only a valid one (`step=manifest-schema`). It records, in `EXPERIMENT_RUNS_DIR/<id>-<run>/experiment-record.json` (private, exclusive, `--execute` only): commit SHA, manifest sha256, resource limits, region, start time and metric locations; `experiment-result.json` adds the end time and exit code. The pipeline part is `run-bounded-pipeline.sh` (called with `--delegated-from-experiment <manifest sha256>`), so the approval, pre-spend, G6, cluster and YARN-kill behaviour is identical; its output is shown prefixed `pipeline| `. Real manifests are written in Phase 15 by the experiment-engineer under `experiments/`; the test fixtures are in `scripts/tests/fixtures/experiment/`.

**Manifest schema** (`scholarchain.experiment-manifest.v1`, JSON; unknown keys are rejected at every level; the cluster id is not in the manifest because Terraform creates the cluster):

| Key | Rule |
|---|---|
| `schema`, `id` (`^[a-z0-9][a-z0-9-]{2,29}$`), `description` | required |
| `budget` | **required**: `max_usd` (number, at most `EMR_MAX_RUN_USD`), `max_runtime_minutes` (10 to `PIPELINE_MAX_RUNTIME_MINUTES`), `max_capacity` (must equal 1 + `core_count` + `max_task_count`, at most `PIPELINE_MAX_CAPACITY`), `region` |
| `teardown` | **required**: `mode` = `auto-termination`, `max_idle_timeout_seconds` (60 to `PIPELINE_MAX_IDLE_TIMEOUT_SECONDS`) |
| `pipeline` | `instance_type`, `core_count`, `max_task_count` (default 0), `input_prefix`, `output_prefix`, `hadoop_submit_jar`, `hadoop_libjars`, `hadoop_config`, `er_jar`, `er_policy`, `er_config`, `spark_config_template`, `datasets_manifest`, `artifact_sha256` (an object that includes `job-jar`); each becomes the matching `run-bounded-pipeline.sh` flag |
| `metrics` | `locations`: a non-empty list of `s3://` URIs |

`--execute` needs the pipeline's approval keys with `APPROVED_ACTION=run-experiment` and `APPROVED_MANIFEST_SHA256`; the dry run prints both the experiment and the pipeline `APPROVAL-LINE:` values.

### Evidence archive (`archive-evidence.sh`)

`archive-evidence.sh --phase 13 --label 13b-v1 --include test-reports=PATH [--include CATEGORY=PATH ...] [--external-location NAME=LOCATION ...] [--tar] [--s3-prefix s3://bucket/key] [--region R]`. Categories: `test-reports`, `plan-receipts`, `image-digests`, `run-manifests`, `metric-exports`, `experiment-outputs`, `release-metadata`. The label directory `docs/agent-runs/phase-NN/evidence/<label>/` must not exist (a new label per run, for example `13b-v2`); every file is created exclusively below a symlink-free directory chain. **Thresholds:** a UTF-8 text file of at most `ARCHIVE_MAX_COPY_BYTES` (1 MiB, inclusive) is copied after redaction (account ids, secret-named environment values, registered private values, private-key blocks, access key ids, any generic `secret`/`token`/`password`/`api key`/`credential` assignment such as `api_token = ...`, `client_secret: ...`, `password=...`, `api_key: ...` or JSON `"secret": "..."` (pure numbers, booleans, null and hex checksums stay), Bearer and Authorization values); a larger file, and any binary file (it cannot be redacted), is **not copied**: `INDEX.json` records its sha256, size and the **required** external location (`--external-location NAME=LOCATION`, an `s3://` URI, `drive:<text>` or a Drive URL; a file without one refuses the run before anything is written). Terraform state, plan binaries, raw plan JSON and plan text, variable files, dotenv files, keys and login material are refused outright; only `*.tfplan.receipt.json` and `*.tfplan.sha256` are accepted from the plan family. Symlinks are refused. **No macOS metadata (item 31):** names starting `._` and `.DS_Store` are skipped and listed in the index; `--tar` builds `<dest>.tar.gz` with Python `tarfile` (sorted, fixed mtime, no owner names) and verifies the listing with `tarfile` and with `tar -tzf` under `COPYFILE_DISABLE=1`. Afterwards the directory is re-read: every copied file must match its archived sha256 and hold no account id, registered secret or credential shape (exit 4 otherwise). `--s3-prefix` is **dry run only**: it prints the `aws s3 cp ... --checksum-algorithm SHA256` commands (and the tar's sha256) for a human to run after reviewing the index.

**Item 31, precisely.** The spike results tarball legitimately contains Hadoop checksum files named `._SUCCESS.crc`; macOS `bsdtar` mistakes them for AppleDouble metadata and `tar -xzf` exits 1 ("Failed to restore metadata") without extracting them. `scripts/phase12d-spike/collect-evidence.sh` therefore extracts with Python `tarfile` (verbatim members; absolute paths, `..`, links and special files refused) and exports `COPYFILE_DISABLE=1`; `archive-evidence.sh` never produces a `._` member.

## Exit codes (all Phase 13 scripts)

| Code | Meaning |
|---|---|
| 0 | success, dry run completed, or (check.sh) every gate ran and passed |
| 2 | usage error |
| 3 | refused: precondition or approval check failed (wrong tool version, dirty or unreadable tree, record or stage mismatch, stale or missing pre-spend receipt, missing or mismatched plan receipt, output path outside `PLAN_DIR` or not ignored, wrong account, policy violation, missing or non-matching confirmation); nothing mutating ran |
| 4 | a verification gate failed (check gate, architecture gate, archive mismatch, plan target mismatch, registry digest or ECS verification failure) |
| 5 | an underlying tool command failed (sbt, docker, terraform, aws); `RESULT: PARTIAL` names an incomplete step |

| 124 | a command timed out (the whole process group was killed) |

## Subphase 13C: main EMR bootstrap, B1 to B5, `tests/infra`

* **`scripts/emr/bootstrap.sh`** (with the installed step programs `sc-step.sh`, `sc-ceiling-check.py`, `sc-class-origin-verify.py` and `sc-render-spark-config.py` beside it, finding C1) is the real bootstrap action of the main EMR module (`infra/terraform/modules/emr`), ported from the Phase 12D spike for decision 12-10. A human uploads it, the runtime archive (G5) and the job JAR in Phase 14; nothing is uploaded before that. Its arguments (all passed by Terraform) are `--region --max-minutes --startup-allowance-minutes --self-sha256 --runtime-uri --runtime-sha256 --job-jar-uri --job-jar-sha256 --spark-defaults-b64 --spark-defaults-sha256 --efs-id --access-point-id` and any number of `--artifact URI,SHA256,DEST` (step scripts and config; DEST under the runtime tree, `/opt/scholarchain-spike/bin/` or `/mnt/scholarchain/config/`). Order: validate arguments, arm `shutdown -h +N` before any download, check its own hash (drift detection, not tamper protection), download the runtime archive and verify its sha256 BEFORE extracting, check every archive member stays inside `scholarchain-runtime/`, install the job JAR (own S3 URI and sha256), resolve Java 17 at run time (never hard-coded) and write the pinned Java-home file, decode the Terraform-rendered spark-defaults and verify its sha256, remove every `JAVA_HOME` entry whatever its separator (leading whitespace, tab, `=`, `:`, space) and append the resolved one so each key occurs exactly once (carried item 29), verify and install each `--artifact` (item 8), mount the EFS access point (`tls,iam`) at the pinned mount and prepare `runs/`, `staging/` and `config/` on the primary. Carried item 28: the resolved Java path must match `^/[A-Za-z0-9_.+/-]+$` with no `..` (a newline, space, `#`, `=`, `:` or backslash could inject another properties line); an unsafe candidate is skipped and, if no safe Java 17 exists, exit 4. Exit codes: 3 sha256 or archive mismatch, 4 Java, 5 EFS, 6 download failed, 10 shutdown timer, 64 usage. Every default path equals the pinned value in `scripts/config/release.conf` (a test compares them). `scripts/tests/test_emr_bootstrap.py` runs it against fake `aws`, `sudo`, `shutdown`, `mount`, `dnf` and `java` binaries.
* **B1 to B4** are described above (step timeouts, run ledger, idle tail, single-use approvals). `--max-idle-seconds` and `PIPELINE_MAX_IDLE_TIMEOUT_SECONDS` are 900 at most. `scripts/tests/test_13c_pipeline.py` covers B1 (a hung `aws s3 cp` in stage-in and copy-out and a hung `hadoop fs -copyToLocal` in the localize copies are killed at the step timeout, using a faithful `timeout` shim), B2, B3 and B4; `test_budget.py` was rewritten for the new estimate and ledger.
* **B5.** The stale `PENDING_UNTIL_POPULATED` exemption is gone from `check.sh` and its tests: a required suite that is missing or executes no test fails every run that reaches it, partial runs included.
* **`tests/infra` is a fifth REQUIRED suite** of the `script-tests` gate (`discover:tests/infra`): the test-engineer's independent Terraform-root tests, which run `terraform test`/`plan` on scratch copies of the roots. The `terraform` gate runs first, so the providers they need are installed; a default full run fails if the directory is missing or executes zero tests. The per-suite timeout is `TIMEOUT_SBT_CHECK_SECONDS` (3600 s), far above the suite's roughly 150 s. `test_check.py` simulates both suites in fixture repositories.
